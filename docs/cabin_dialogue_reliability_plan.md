# 客舱对话：重复下单、会话冷启动、慢回复与现场日志修改方案

**评审稿 · 2026-11-23。** 面向 Moss 服务端、平板、订单/设备后台、模型服务和现场运维。本文是修改方案，不是已发布的功能。现场参照主镜像 `f2662e56-arm64`；代码对照本工作树 `14e8a9d7`。保持主服务容器化，保留客舱 Agent 和现有运行隔离；不要求现场把全局 runtime 切为 `host`。本轮不修改产品代码、不重放现场订单或设备动作。

## 一、先定范围和优先级

| 优先级 | 事实与边界 | 要改变的结果 |
|---|---|---|
| P0 重复交易 | 11 月 20 日 4 次成功转写后，各有一簇 4 条独立聊天；第一簇在 7 ms 内全部到达。当天 12 次创建接口业务成功，不等于乘客说了 12 遍、也不等于确认落库 12 笔可乐。 | 同一用户提交即使被发 4 次，只建一单；真实的“再来一杯”仍能建第二单。 |
| P0 重复设备动作、假等待 | 11 月 18 日一条暖会话在工具后明确报模型停滞，外层又等 27.116 s，随后重跑 16.927 s。原会话和重建会话的工具均留下“已下发”的回执；最终动作次数需设备审计核实。 | 一个执行主体；失败能立即结束；执行结果不明时不自动重放。 |
| P1 冷启动固定成本 | 原镜像、同一模拟模型、无会话容器：公网目录立即失败时，三个冷座首字 194–262 ms；目录接受连接但不响应时 10.17–10.23 s。请求的是模型目录，不是模型权重。 | 固定模型客舱会话初始化阶段对公网目录 **零请求**。通用会话仍可切换模型。 |
| P1 语音及普通对话长尾 | 18 日成功 ASR 中位 250 ms、P95 20.352 s；20 日两次重叠 ASR 分别 13.170 s、28.170 s。18 日 25 条未超时重建的 Agent 聊天扣播报后中位 4.992 s、P95 13.150 s。 | 分清识别排队、模型首个有效文本、工具往返、服务端缓冲和客户端渲染，再决定怎么改。 |

**对照基线：** 20 日 16 条聊天均未走 Moss Agent；逐条扣除整段播报后仅 54–180 ms。18 日另两条重建请求即使扣掉播报也要 62.142 s 和 63.302 s。19 日附件无可分析对话。现有样本不是关闭音频后的压测，也没有客户端首字或订单库证据。

## 二、先止损：让一次提交只产生一次业务动作

### 2.1 平板、Moss、订单服务使用同一个操作标识

**拟议接口，不是现场已有字段。** `request_id` 仍由 Moss 为每次 HTTP 请求生成，用于判断平板确实发了几次；另加稳定的 `client_message_id`，表示一次用户提交。不能拿每次重新生成的 `request_id` 来防重。

| 环节 | 修改及行为 |
|---|---|
| 平板/语音入口 | 在开始一次录音或用户点击发送时生成一个随机 ID，**在注册/触发异步回调之前**保存。一次录音、其转写完成回调、网络重试、页面恢复后重发，都沿用同一 ID；用户主动再发一次才生成新 ID。同时修监听器重复绑定、页面销毁未解绑或多个发送实例的问题，但不假设原因一定在平板。 |
| `POST /v1/voice/query` | 接受并回传 `client_message_id`；可同时返回服务端 `voice_message_id`。已完成的同 ID 识别重试可复用结果，不再次写入用户语音消息。旧平板没有 ID 时仍可转写；**仅改服务端响应而平板不回传，不能解决四次建单**。 |
| `POST /v1/ai-chat/send` | 接受同一 ID（纯文字同样适用）；先鉴权、确定会话范围、原子认领，再写聊天、更新上下文、调用工具。已有转写记录按引用关联，不凭“最新一条相同文字”匹配；用户编辑转写后遵循一次明确提交的语义。单接口 `POST /v1/voice-chat/send` 也走同一认领逻辑，不与两步式调用叠用。 |
| 订单服务 | Moss 为本次提交对应的业务动作派生稳定 `action_id`（一轮多动作时含动作序号），随创建请求传入。订单服务在写订单的事务内做唯一性约束；同键同内容返回原订单号和状态，不创建第二笔。同样约定取消动作。 |

**Moss 存储设计：** 在 `CabinStore` 增加持久化提交记录：经鉴权的会话范围、`client_message_id`、规范化输入指纹、状态、结果引用和过期时间；为 `(scope, client_message_id)` 建唯一约束。范围含租户/业务对话及乘客或座位绑定代际，座位换人不能读出旧结果。认领只用短事务，不在数据库事务里等待模型或 HTTP。多实例若不共享这份数据库，不能靠本地唯一索引跨实例去重，订单后台的唯一键仍是最后保障。

| 重复到达时的状态 | 处理 |
|---|---|
| 新提交 | 只有认领成功的一方允许创建订单、控制设备、写助手回复或启动播报。 |
| 同键同内容，仍在执行 | 复用正在执行的结果，或返回明确的 `in_progress` 让新版平板按 ID 查询；不能再启动一轮。对旧 SSE 客户端保留已协商的响应形状。 |
| 同键同内容，已完成 | 返回原结果/订单引用；平板按同一消息 ID 更新原气泡，不再增加气泡、播第二次或建单。 |
| 同键不同内容 | 返回冲突（建议 HTTP 409，发 SSE 头前判断）；不覆盖原记录、不执行。 |
| 下游超时、进程在建单后崩溃 | 标记 `outcome_unknown`。按业务键查单对账；下游没有幂等和查询能力时，只能提示“正在核实”，不能补发创建。不能用短租约到期就再建一次。 |

**兼容策略：** 先发布可选字段和覆盖率日志，再按平板版本/测试座位开启强制模式。旧平板无 ID 时，不按文本、座位、几秒时间窗硬去重，否则会吞掉真实加单。若现场已出现重单、下游又不能对账，在该座位临时禁用自动创建，保留澄清/人工服务，比承诺“保证不重”安全。幂等保留期至少覆盖客户端重试、离线重发和对账窗口，不能跟登录 token 一起过期。先核实 20 日 14:34:14 和 14:35:44 的真实订单号，再决定如何处理存量记录。

### 2.2 设备指令只让一个主体执行

代码里有一个能直接修的缺口：`runtimeService.ts` 为客舱设置 `CABIN_CONTROL_MODE=emit`，但 `dockerBackend.ts` 构造 `docker exec/run` 的环境白名单没有它；`cabin-control.mjs` 在未设置时默认 `execute`。这与现场“工具已经报下发、主服务随后仍有硬件调用”的证据吻合。不能只改技能提示词，也不能据此断言设备最终动作数。

1. 补 Docker user/session 两条路径的透传；在**客舱托管**模式将缺失/非法模式改成拒绝执行，不能静默退回 `execute`。保留显式授权的非客舱独立执行用法。验证真正安装到运行镜像/工作区的脚本，不能只验证源码和主镜像。
2. 工具只产出经 schema 校验的指令；真实设备 HTTP 只由 Moss 的业务层发出。调整脚本目前先检查控制地址、后判断 `emit` 的顺序，使只生成指令不依赖设备地址或鉴权。审计其他客舱技能依赖后，不向只需生成指令的执行环境暴露控制写凭据；可行时限制其直连控制写接口。保留必要的无副作用状态查询。
3. Moss 以 `action_id` 记录 `prepared → sent → acknowledged/unknown`，按真实业务回执生成乘客确认。已下发或状态未知不重发；未知只能查询状态或人工确认。设备端能按键防重则一起接入；否则不能声称端到端“恰好一次”。

## 三、消除 sudorouter 的 10 秒等待

**根因：** 当前 host/scode 和 Docker 两个 backend 在写 `sudocode.json` 前，都先 `await buildAllModelsConfig(baseUrl)`，再 `ensureOpenAIModelConfig(...)`。目录查询实际上访问固定公网 `specific_pricing`，超时 10 秒；24 小时缓存是当前 runner 进程内变量，新进程不继承。把 `llmBaseUrl` 改成本地地址并不能绕过它，缩短全局超时只会缩短症状。

**选择固定模型路径，不选择延长缓存。**

1. 由主服务根据持久化 `session.source === 'cabin'` 和有效客舱模型配置决定策略，通过受信任的 runner 参数/manifest 明确传 `modelCatalogPolicy=fixed`；新鲜、恢复、重建和重启后路径相同。通用会话默认 `dynamic`。该名字是拟议内部字段，不是要求客户现在填的 JSON；不按 URL 长相或用户传的任意环境变量识别客舱。
2. 抽出两个 backend 共用的配置函数。`fixed` 直接用 `ensureOpenAIModelConfig({}, selectedModel)` 生成唯一 provider 条目，并使用显式配置的 base URL/凭据；**不调用目录函数、不后台刷新、不以失败为由回落公网**。固定模式配置不完整、别名不匹配或文件写入失败时返回可定位的配置错误。`dynamic` 保留原有目录/缓存/模型切换行为。
3. 统一配置文件里 alias、启动参数和 provider 的原始模型 ID。特别覆盖现场以 `/Users/.../模型名` 作为模型 ID 的情形，以及 `proxy/...` 与普通短名；它是上游接受的模型标识，不要把它当成本机文件路径裁剪。写配置按会话隔离，避免多个冷座位覆盖同一个 `sudocode.json`；host 共享配置目录的问题不作为要求客户切 host 的理由。
4. **验收分两层：** 单测注入会抛错的目录客户端，固定模式调用数必须为 0、通用模式仍可列/切模型；再用最终镜像和本地模拟模型对照“目录正常 / 拒绝 / 连接后无响应 / DNS 不通”。四种情况下固定模式均能成功回复，受控目录探针请求数为 0；同机多轮冷启动的首字差不再随公网黑洞增加约 10 秒。分别跑 Docker user/session、主容器内 host 兼容路径，并验证旧获准 runtime 镜像组合。**目标是去掉固定额外开销，不是承诺现场大模型 200 ms 出字。**

**进一步减少冷启动次数（独立后续项）：** `ensureConversation` 现在会在第一次语音识别/聊天前创建完整 Moss 会话。可拆分“建业务对话”和“首次确需 Agent 时绑定 runner”；识别、订单、直控不预先建 Agent。`moss_session_id` 当前非空，不能只删除创建调用：要先设计可空关联/绑定表、并发原子绑定、孤儿回收、重启恢复及旧记录迁移。先完成零公网和正确性修复，再独立灰度，不把三项捆绑发布。

## 四、消除 Agent 故障放大，治理 ASR 和首字

**Agent 终止与恢复。** 明确协议 `turn_started → progress/tool → turn_completed | turn_failed`。一个尝试只能有一个终态；用 `turn_id + attempt_id + prompt_rpc_id` 关联。scode 如已返回对应 JSON-RPC error，ACP bridge 直接映射；若打包版本只给自然语言错误而不发终态，需改 scode/适配层并锁定兼容版本。不得靠匹配中文“请求超时”或解析 stderr 判定业务终态。旧 runner 不能提供结构化事件时，保留总截止时间、向上报 `unknown`，不盲重试。处理断连、迟到的旧结果和并发：同一个 runner 暂不支持按轮隔离输出时，每次只允许一个在途 Agent turn；其他座位不串行。超时后旧结果不得交给下一轮。

| 观察到的情况 | 对乘客与系统的行为 |
|---|---|
| 上游明确拒绝、鉴权错误、固定模型不支持 | 立即失败，记录错误类别，0 次重建。流式 HTTP 200 只代表响应头，不记为推理成功。 |
| 工具后模型停滞，但 Moss 有可信业务成功回执 | 不再让模型复述；从回执直接生成准确确认，不重跑工具。只有工具旁白、无可信回执则不能宣称成功。 |
| 已派发但结果未知 | 返回“正在核实/请稍候”，关联 `action_id` 对账，不自动重放。 |
| runner 在提交前丢失，或可证明是无副作用的纯读轮次 | 只在总 deadline 剩余且未超出策略上限时重建；整次交互共用预算，不给每次重试重新发一份 45 秒。 |

补上 `readServerConfig()` 对 `replyTimeoutMs`、`sessionRecoveryEnabled`、`sessionRecoveryMaxAttempts`、`contextReplayTurns` 的透传和生效测试。当前 `maxAttempts` 主要是 `> 0` 开关且用 `recovered` 限为一次，要么实现可配置上限，要么发布前约束为受支持值；无论配置多少，有副作用且状态未知都不重试。**不建议现场先单纯把 45 秒调小。**

**ASR 与普通聊天。**

- 输入语音：同一录音/同一 ID 只做一次识别；相同文字、不同录音不能合并。用同一组合成短录音分别做 1、2、4 路同座与跨座测试，固定音频长度并区分冷/暖模型；上游分别记录入队、开始推理、结束。在拿到这些数据前，不归因为 GPU 不足，也不先对所有座位强制串行。如果确认排队，按模型实际吞吐做有界队列、每座公平限制、过载提示和无重复提交的取消/重试策略。
- 普通对话：优先补足已验证的高置信设备说法；歧义走澄清。在可证明是**无工具**的闲聊路径才放开真实内容流式下发；副作用路径等业务回执。18 日有一次订单分类先花 8.679 s 又走 Agent 3.505 s：单独记录分类耗时、命中率和模型调用数，再决定是否把已确认的变体改为规则；不要让每轮双调模型。
- 输出音频继续独立：现场使用已有 `cabin.conversationSeatAudioEnabled=false` 作为基线，不影响输入 ASR，不等于关闭飞行自动广播。当前分支 `enabled` 语言路径已经可以先发文字，但 `done` 仍等播报，现场旧版订单会连文字一起等。先让平板在第一个有效 `delta` 渲染；将来恢复音频时，若需要让 `done` 也提前，应协商新协议（如 `audio_pending` 和独立后续状态），不能悄悄改变旧 `done.audio_playback` 的含义。

## 五、现场观测：一次录音能查完整条链

复用现有 `cabin.jsonl` 和 runner 日志，不强依赖外网或引入新的观测平台。`CabinLogger` 现有 `request_id` 是单次 HTTP 粒度，写盘异步、已有 50 MiB 轮转；`agent-reply.elapsed_ms=0` 不是回复只用 0 ms。保留旧字段，新增版本化事件和**每次请求一条汇总**。

| 标识 | 作用与传播 |
|---|---|
| `client_message_id` / `turn_id` | 用户一次意图 / Moss 认领后的逻辑轮次；ASR 请求、聊天重发、SSE 和平板渲染串在一起。不同重试保留不同 `request_id`。 |
| `attempt_id` / `prompt_rpc_id` / `model_call_id` | 区分 runner 的不同尝试、同一轮中的第几次模型调用；在可控模型代理传关联头，不能传时记本端映射。 |
| `action_id` / `receipt_ref` | 对齐建单、控制回执、对账；业务订单号仅在受限审计表保留，运维日志用不含业务明文的引用。 |

**拟议事件与负责方：**

| 层 | 必记事件/指标 | 用来回答 |
|---|---|---|
| 平板 + 网关 | `recording.finished`、`asr.result_received`、`chat.send_attempt`、`proxy.forward`、`ui.first_text_rendered`；含客户端版本、发送序号、触发来源 | 是平板发了 4 次、代理发了 4 次，还是 UI 渲染了 4 次？ |
| Moss 入口 + ASR | `request.accepted`、`turn.claim`（new/join/replay/conflict）、`asr.upstream`、`route.selected`；录音时长/字节、在途数、路由，不记内容 | 一次用户意图对应几个请求？慢在识别还是在路由？ |
| 会话准备 | `session.prepare` 分解业务对话、runner 获取/创建/复用、容器 create/start 或 exec、socket 可连、模型配置、ACP ready；记录 `runtime_type`、`container_mode`、`catalog_policy`、`catalog_fetch_count`、`cold/reused`、镜像/技能版本 | 是建容器、初始化 runner，还是又访问了云目录？socket ready 不等于模型能回复。 |
| 模型与工具 | `model.request`、`model.headers`、`model.first_nonblank_text`、`model.finished/failed`、`tool.proposed`、`action.dispatch/result`、`turn.recovery_decision` | 返回 200 后多久才有正文？调用几次？失败后为什么重试或不重试？ |
| 回包 | `sse.start`、`sse.first_content_delta_written`、`sse.done`、`request.summary`；输出音频启用时另记合成和上传时长，关闭记 `skipped` | 文字是在服务端被压住，还是平板收到后没展示？服务端写出不等于客户端收到。 |

**实现约束：** UTC ISO 时间用于跨服务关联；进程内用单调时钟算 `duration_ms`，设备上也用本地单调时钟量渲染。跨机未校时，不相减推断延迟。汇总包含状态、路由、总耗时、各段、模型调用数、重建次数和是否有副作用；并发/嵌套阶段明确标记，不重复相加。没有上游支持的 `queue_ms`、`inference_ms` 填缺失，不伪造 0。不要写每个 token、每个音频块；错误、慢轮、重试、幂等冲突、交易结果全记，正常细分阶段可采样。高基数 ID 只进日志，不做指标标签。

**隐私与可用性：** 用字段白名单处理 `details`、嵌套对象、错误和 URL；默认不记音频、输入/回复全文、模型请求体、鉴权头、密钥、完整乘客/平板身份。现场原始 scode debug 能含请求体/头；常态关闭该类调试或做源头脱敏，故障需限时、限座开启，不能靠事后删报告。按绑定生成脱敏关联引用，限制导出权限。写日志设有界缓冲、轮转保留天数和总容量（由现场定），监控丢弃计数；日志满/失败不阻塞聊天。订单账本是持久化业务事实，不受日志采样和丢弃影响。

**拟议交付：** 离线 `cabin-trace` 小工具，按上海日期窗口及 `turn_id`、`request_id` 或 `action_id` 查找，以相对毫秒列出所有尝试、业务回执和首字，给出“缺哪些层的证据”。首版也应能读旧日志：旧数据的 ASR/聊天只有时间和会话相邻时标为“推测关联”，不要伪装成同一提交。下面是新增事件的**示意**，不是现场数据：

```json
{"event":"turn.claim","request_id":"req_demo_2","turn_id":"turn_demo","client_message_id":"msg_demo","outcome":"join"}
{"event":"session.prepare","turn_id":"turn_demo","attempt_id":"att_demo","catalog_policy":"fixed","catalog_fetch_count":0,"duration_ms":42}
{"event":"turn.recovery_decision","turn_id":"turn_demo","attempt_id":"att_demo","error_code":"MODEL_POST_TOOL_STALL","action_state":"acknowledged","decision":"use_receipt_no_retry"}
```

**值班人员怎么判断：** 同一 `client_message_id`，平板 4 次 send、网关 4 次 forward → 看回调/客户端重试；平板 1 次、网关 4 次 → 看代理重发；Moss 4 次 accept 但 1 次 dispatch → 防重生效；1 次 dispatch 对上多笔订单 → 查订单后台。慢请求先看实际路由，再分别比 ASR、`model.first_nonblank_text`、`sse.first_content_delta_written`、平板首字；没有平板埋点时不要把服务端写出当成乘客已看到。现场即使未升级，也可先按现有 `request_id` 导出最小事件清单（需 `jq`，不导出正文或凭据）：

```sh
jq -c --arg id "$REQUEST_ID" 'select(.request_id == $id) | {time,type,path,upstream,elapsed_ms,ok,error_code}' "$CABIN_LOG_FILE"
```

**验收与灰度：** 先用本地桩服务、合成录音和假设备/订单库，不用客户真实订单测试。将回归加入 `.github/workflows/build-release.yml` 对导出的 ARM64/AMD64 最终镜像执行（复用 `docs/cabin_image_smoke` 对照思路），而非仅验证源码单测。性能样本报数量、冷/暖、配置；建议每档至少 30 次，发布前按现场基线再定真实硬件阈值。零公网、零重复业务动作属于正确性门槛，不以均值代替。升级前备份业务数据库与配置，使用新增表/可选字段做向后兼容迁移。

**上线顺序：** 现场先关闭对话播报，确认无该轮 TTS 请求、ASR 仍正常；在测试座用“只澄清、不执行”的语句对齐平板和网关。A、B 及 C 的兼容接收可以先灰度；只在客户端回传 ID、后台可幂等/对账后对该座开启写动作强制模式。D 必须服务端和 scode 协议兼容，同机验证再扩大到其他座位。分别保留旧主镜像和 runtime 组合，不动历史会话。

**回退红线：** 出现重复单、重复设备下发、跨座结果或日志泄密，先停受影响写动作/导出，不清业务幂等账本，不自动重放，也不靠恢复旧镜像重做未决操作。只回滚本次灰度功能，保留对账通路。离线现场不能以“打开公网目录”作为固定模式的自动回退。不同提交同时改了语言/音色，是否一起发布应单独批准，不把当前 worktree 的其他改动捆入现场热修。

**需评审确认的两个外部依赖：** 平板团队能否为一次录音生成并透传稳定 ID、提供发送/渲染日志；订单/设备后台能否接受操作键并按键查结果。即使两项暂时无法落地，也能先交付固定模型零公网、Docker 意图模式修复、错误停止重放和服务端分段日志，但不能对现场承诺端到端恰好执行一次。
