一句话结论。就 moss 今天的拓扑而言,nexus 的 auth 是纵深防御,不是在补一个开着的门。真正承重的那面墙是 :2126 的 loopback 绑定。所以我们要做的第一件事不是「上 auth」,而是让「无 auth + 非 loopback」这个组合在内核里不可能存在。

2. 但承重墙只有一面 对 moss 今天跑的 v0.4.0 仍成立

整个隔离模型压在一个假设上:「除了 proxy,没有别的东西能碰到 :2126」。

这个假设离失效只有一行配置。

把 MOSS_NEXUS_GRPC_PORT 指到非 loopback、或者把 nexus 挂进 moss-network、或者 proxy 出一个 SSRF/RCE —— 空 token 意味着任何 session container 可以直接读写所有租户的 secrets,绕过整个 proxy 策略层。而且没有第二道防线。

这是 moss 侧同学自己指出来的,原话是 "The single load-bearing control is the loopback bind ... it's one config line away from a serious multi-tenant breach"。这个判断是对的,而且比「要不要上 auth」本身更要紧。

✅ 这个洞已经在 main 上堵住了(§3,PR #143)。但 moss 今天跑的 v0.4.0 里还没有 —— 所以本节描述的仍然是你们生产上的现状,直到 bump。

3. 这条不变量已经焊进内核了 已合并 · 未发版

✅ 已实现并合并(nexus-vfs PR #143)。下面这张决策树现在是 nexusd-cluster 的真实行为,四条路径都用真 daemon 验过,并且进了 CI。

但 moss 今天还拿不到 —— 它不在任何 release 里(最新 release 仍是 v0.4.0)。这是 §8 里「发 release」那一步要解的。

与其靠 code review 盯住那行配置,不如让内核拒绝这个组合存在:

无 auth 只允许在 loopback 上。绑非 loopback 地址,必须开 auth(sk- token)或 mTLS —— 否则 daemon 拒绝启动。

顺便更正一处术语(因为它会影响你们读我们的架构):AuthProvider 不是 HAL,它是 transport 层的一个 DI 槽(Arc<dyn AuthProvider>) —— 内核根本不消费它。真正的 HAL 是 AuthKeyStore(§3.B.3),那是凭证记录的复制存储。两者正交:换存储不动策略,换策略(JWT/OIDC)不动存储。

4.1 每个平面产出什么身份

一次判定落在 OperationContext.agent_id 上的东西,取决于走哪个平面 —— 这三条路各产出一层不同的身份:

平面 / 凭证产出的身份agent_id
cert 平面 · Agent 证书(mint --subject-type agent <name> 签发,SAN nexus://agent/{name})agent 身份 —— 稳定名字。cert 是纯身份(DID),不带授权= name
cert 平面 · Node 证书集群节点成员身份(SAN nexus://zone/{z}/node/{n})无
token 平面 · User / Service key(sk-)对应的 user / service subject无

只有 Agent 证书这一条产出 agent_id,它就是消息署名(A2A 里被内核 stamp 成不可伪造 from)的发送方身份 —— A2A 侧怎么用见 nexus-integration-architecture §3.3。cert 平面按 SAN 类型分流:node SAN → 节点成员身份(让联邦复制状态),agent SAN → agent 身份(让消息有可信来源)。两者正交:一层管传输成员、一层管内容署名。

agent 证书是一张纯身份(DID):它声明「我是谁」,SAN 就是全部内容 —— nexus://agent/{name},由持有 CA 私钥的 founder 签发。一张有效的 agent 证书就是一个 mailbox 参与者:它对 mailbox 的写授权由 A2A stamp hook 掌管 —— stamp hook 在写 mailbox 时要求 agent_id(缺则 fail-closed),并把 from 盖成该 agent(§5),这一个接缝同时完成「授权这次写」与「让署名不可伪造」。授权就是「mailbox 参与者」这一身份本身,不经 zone:zone 门管的是「某 zone 的租户」,agent 是参与者,所以 agent 的判定上下文只承载身份(需要 zone 授权的主体持 user/service 的 sk- key)。跨节点成立的关键是验证挂在 CA 上:任意节点用集群 CA 验 agent 证书即得其身份,无需查凭证存储(auth store 是 root-SOLO、每节点独立、不复制),所以同一张 cert 在任意节点认证结果一致 —— 这也是 §5「验证挂 CA、不挂 per-node store」的兑现。唯一性:auth mint 在 founder 存储内强制同名唯一(--allow-existing 留给轮转),cert 是身份的单一来源(SAN 形式与节点平行)。吊销走 CRL —— cert 由 CA 全集群签发,吊销就由 CA 全集群分发,同源同域。

部署落地:cert 与 token 两个平面按凭证种类分面。可达的 mTLS bind(--bind-addr,如 Tailscale IP,强制 client-cert)承载 cert 平面 —— node 与 agent 都在这里(都是 CA 签发的证书;mTLS + client-cert 天然可跨网,不像明文 bearer token 有暴露风险),resolve() 按 SAN 类型分流成节点身份或 agent 身份。user/service 的 sk- token 经一个 loopback token bind 承载 token 平面(明文 bearer 只留环回,不上可达面)。于是 §3.1 的「--no-tls ⊥ sk- token」仍成立:cert 面握手层强制 mTLS,token 面只在 loopback。cert-agent 的 mailbox 写由 stamp hook 盖成不可伪造 from(§5)后经 raft 复制到对端,任意节点用 CA 重验。

moss 侧提的两层方案,我们的机制都能直接承接:

moss 侧的提法我们的对应物判断
Tier 1 daemon 全局 auth token(一个共享 secret,常数时间比对) 直接用 sk- key:moss 在 NexusManager.start() 里铸一把,传给 daemon 和 NexusClient 开箱即用。代码量和「共享 secret」一样,但白送吊销/过期,以后要按 org 拆也不用换机制
Tier 2 per-namespace scoped token(签名 token 里带 allow: ["/secrets/org/{orgId}/*"],每次 RPC 校验路径前缀) OperationContext.zone_perms + 内核权限门 —— 这个接缝已经在 context 里了 同意不急。它只有在「你不完全信任 proxy 的 namespace 解析」时才值。真要上的时候接口已经在那儿了

有了第 3 节那条不变量之后,Tier 1 对 moss 就变成了可选的纵深防御(因为 loopback + 无 auth 已经合法且安全)。所以这里需要 moss 侧拍一下:是现在就上 Tier 1,还是先只要 loopback 守卫?

5. 不可伪造的 authorship — 跨信任域可验的 agent 署名

§4.1 里,Agent 证书是唯一产出 agent_id 的凭证,内核把它 stamp 成 mailbox from。本节把这个 from 从「本集群内因内核盖章而可信」提升为一个可携带、任意消费方(本机 / 跨节点 / 跨组织)都能独立密码学验证的属性 —— 每个 agent 的署名各自成立,不依赖 ingress 节点的姿态。

5.1 Agent 身份 = 一张 CA 签发的证书

agent 身份与节点身份同构:同一套 certgen(EC P-256 + URI SAN)、同一个 cluster CA 签发,SAN 用 §4.1 已预留的 canonical 形式 nexus://agent/{name}(与节点的 nexus://zone/{z}/node/{n} 平行)。CA 私钥留在 founder,agent cert 走与 node enrollment 同一条签发路径。使用姿势不变 —— auth mint --subject-type agent --subject-id <name> 仍是一条命令、一个产物(一份 cert 包),和铸一把 sk- 一样开箱即用;agent 用这一张 cert 同时完成认证(peer_identity 解析 nexus://agent/ → agent_id)与署名,身份只有一个来源。

5.2 署名如何被任意消费方验证

agent 用私钥对 envelope 签名,签名与其 cert 随 payload 一起进 mailbox。任意消费方的验证是三步:① cert 在 cluster CA 信任链下有效;② 签名在 cert 公钥下有效;③ cert 的 SAN 名 == envelope 的 from。三者皆真,则 from 为该 agent 亲笔。

验证挂在 CA 上,不挂在凭证存储上 —— 这让三件事同时成立。(a) auth store 保持每节点独立(§4.1 的 root-SOLO 不变量原样保留):跨节点验签靠每个节点都持有的 CA,而非复制存储。(b) 跨节点:签名的 envelope 经 raft 原样复制到对端,对端以 CA + 公钥重验。(c) 跨组织:换成跨 CA 的信任锚即可,沿用 X.509 —— 这是 nexus A2A 面向跨组织协作的自然延伸。

Prior art.本节的署名-验签模型借鉴 BlockA2A(Zhenhua Zou、Zhuotao Liu 等,清华大学;arXiv 2508.01332)对 agent-to-agent 的 DID 消息验证(其 Protocol 2:发送方以私钥签、接收方按可解析公钥验)。nexus 把这一模型落在自身已有的原语上 —— CA 签发的证书作可解析身份、raft log 作有序防篡改的强一致账本、内核权限门作访问控制 —— 在集群内获得零额外信任基座,并保留向跨组织(跨 CA)扩展的路径。

5.4 跨组织:一个问题裂成两个锚 提议 · 未实现

§5.2 那句「跨组织 —— 换成跨 CA 的信任锚即可」,这一节把它展开(§5.1–5.3 是集群内已合并的域内模型,5.4 起是它的跨域扩展)。先钉定义:cross-org ≡ cross-CA ≡ cross-trust-root。信任边界是 CA,不是机器、不是 org 标签、不是在不在同一个 LAN —— 两台在两家公司的盒子共用一个 CA = 一个信任域(是 federation,不是 cross-org);一台盒子自签自己的 CA = 另一个信任域(才是 cross-org)。典型载体:一台交付到客户侧、自带 CA 的 DGX,它永不加入我们的 raft cluster,只把署名后的消息经隔离中介(平台 broker)过界。

关键动作:今天(§4)成员资格和署名都压在同一个 client_ca_root 上;cross-org 把这两件事掰开 —— 这是整个扩展的地基。

两个锚,各管一件事。(1) 成员资格锚 = 我们的 CA(client_ca_root),只答「它是不是我 raft cluster 里的节点」—— 外部盒子永远不是成员。(2) 署名锚 = 一张外域 authorship 锚点注册表(外域 CA 指纹 → 信任域 id),只答「这个 from 是不是某个我登记过的 org 的真 agent 签的」。两者分开存、分开判。

命名 —— 域内扁平,过界时限定。每个信任域内部照旧扁平(nexus://agent/{name},外域用它自己的 mint 保证域内唯一),cert 格式一字节不改。全局唯一由验证方在过界时合成 {信任域}/agent/{name}(如 hospital-a/agent/cardio-expert);canonical org = f(验证用的 CA),不是 SAN 里的自由文本 —— 信任域串是我们注册那张外域 CA 时钉的,外域无法自称 hospital-a,除非我们把它的 CA 登记成 hospital-a。

授权结论同 §5:agent = mailbox 参与者,句号;外域链永不解析成 node / 成员 / zone 权限

验证仍是 §5.2 的三步,只有第 ① 步的信任锚从「cluster CA」扩成「client_ca_root ∪ 外域锚集」,命中外域锚时给身份打上信任域标签:

6. 对 moss 的具体影响 要你们确认

6.1 必须改:--bootstrap-mode 已经被删了

moss 现在传 --bootstrap-mode static(nexusManager.ts:87)。这个 flag 在 nexus 的 Phase G 已经删除 —— 现在 daemon 自己从磁盘状态推断,不需要 operator 声明。

意味着你们 pin 的是旧版 nexusd(nexus-vfs 0.4.0,经由 copyFromSudowork() 从 sudowork 的安装拷过来)。下次 bump 到当前 release,clap 会直接报 unexpected argument 起不来。

⚠ 这两件事必须原子地一起做,单独做任何一个都会挂。

  • 现在就删掉参数 → v0.4.0 里 --bootstrap-mode 是必需的("--bootstrap-mode (or NEXUS_BOOTSTRAP_MODE) is required"),删了当场起不来
  • 先 bump 不删参数 → 新版里这个 flag 不存在,clap 报 unexpected argument,同样起不来

所以:删参数 + bump 版本,同一个 PR。

而且现在还不是 bump 的时候 —— nexus-vfs 最新 release 是 v0.4.0(6/24),而所有 auth 工作在 main 上,落后 215 个 commit,还没发版。等我们把 loopback 守卫 + auth 折进 nexusd-cluster 做完并发一个 release,你们一次 bump 到位,不用做两遍。

另注:bump 实际要动的是 sudowork 的 runtime-versions.json + COS 上的产物(moss 的 nexusd 是 copyFromSudowork() 拷来的),不是 moss 自己。

6.2 会变:root zone 现在无条件创建

凭证记录存在 raft 树里,所以 daemon 必须有一个 raft group。我们刚把「无联邦时不建 root zone」这个模式删掉了 —— 现在每次启动都会建一个 SOLO 单-voter 的 root zone。

  • 数据目录里会多出 <data_dir>/root/raft/(一个 redb 文件)
  • 多一个 10ms tick 的 transport loop(不在任何 syscall 路径上)
  • 文件 syscall 的热路径不受影响 —— / 仍然走本地 redb metastore,不进共识。root 的 raft group 是控制面,不是数据面

6.3 可能是白捡的:Readdir 是有的,SQLite 索引可以删

moss 侧的判断是「the Rust VFS has no list/readdir」,因此维护了 ~/.moss/nexus/secrets_index.db 这个 SQLite 索引。这个前提不成立。

我先认领一个我自己的不合格。我最早给你们这条建议时,验证是打了折的:你们的命名空间是 org:{orgId}:system,路径里带冒号;而 VFS 会把路径映射成宿主文件名,Windows 直接 InvalidFilename 拒绝。所以我当时把命名空间换成了无冒号的形状才验通 —— 也就是说,你们的真实路径形状,我从来没验过。

拿一个「为了通过而改了输入」的测试,去建议外部团队删代码,这不合格。已经补上了。

现在是在 Linux 容器里、用你们的真实路径形状(带冒号)验的,而且进了 CI(nexus-vfs PR #144):

写入  /secrets/org:acme:system/{openai,anthropic,slack}.json   → ok(空 token)
读回  /secrets/org:acme:system/openai.json                     → 逐字节一致

Readdir("/secrets/org:acme:system")  → ['anthropic.json', 'openai.json', 'slack.json']
Readdir("/secrets")                  → ['/secrets/org:acme:system']

namespace 层和 key 层都能列。那个 SQLite 索引确实是冗余的,而且它是一个需要和 VFS 保持同步的第二 SSOT —— 删掉它是净收益。

一个 API wart:ReaddirEntry.name 返回的是全路径而不是裸文件名。迁移时注意。

6.4 一个隐含约束:namespace 里的冒号

orgNamespacePrefix() 产出的是 org:{orgId}:,路径里带冒号。VFS 会把路径映射成宿主文件名 —— Linux 上合法,Windows 上直接 InvalidFilename 写不进去。你们跑 Docker 所以今天没事,但这意味着 moss 的 nexus 数据目录不能在 Windows 宿主上落地。

6.5 我们替你们守着这个形状 已合并

nexus-vfs 的 CI 里现在有一个 job,叫 "moss's deployment shape, in a container"。它在容器里跑你们的真实形状:

  • 你们的调用参数(nexusManager.ts:84-88 逐字照抄,减去要删的 --bootstrap-mode)—— 这等于我们替你们把 bump 先跑了一遍
  • 你们的真实路径 /secrets/org:{orgId}:system/{key}.json,带冒号

  • 那个致命错误:容器里绑 0.0.0.0(= 挂进 moss-network)—— 必须拒绝启动

⚠ 但这个测试的 fixture 是你们的代码。如果你们改了 nexusManager.ts 的启动参数、或 secretSubject.ts 的命名空间形状,我们这个测试会继续测一个化石,而且照样绿 —— 然后你们 bump 的时候才发现。

所以这是一条契约:改了这两处,请告诉我们一声(或者直接在 nexus-vfs/tests/docker/moss_shape_probe.py 提个 PR 改掉)。我们会同步。

7. 不归 nexus 管、但更严重的那条

moss 侧自己排的第一风险:SYS_ADMIN + seccomp:unconfined + 挂载 /var/run/docker.sock 到 moss-server(deploy/docker-compose.yml:11,17,19)。

这条我同意确实比 nexus 这边严重得多,建议 moss 侧单独立项 —— 不在本文档范围内,但不写出来不诚实。
