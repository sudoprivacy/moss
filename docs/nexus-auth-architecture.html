Nexus 认证架构 — moss 集成对齐

写给 moss / nexus 两边的工程同学。目的:把「nexus 到底需不需要 auth、需要什么样的 auth」这件事一次讲清,并把要一起拍的决定摊出来。

一句话结论。就 moss 今天的拓扑而言,nexus 的 auth 是纵深防御,不是在补一个开着的门。真正承重的那面墙是 :2126 的 loopback 绑定。所以我们要做的第一件事不是「上 auth」,而是让「无 auth + 非 loopback」这个组合在内核里不可能存在。

2. 但承重墙只有一面

整个隔离模型压在一个假设上:「除了 proxy,没有别的东西能碰到 :2126」。

这个假设离失效只有一行配置。

把 MOSS_NEXUS_GRPC_PORT 指到非 loopback、或者把 nexus 挂进 moss-network、或者 proxy 出一个 SSRF/RCE —— 空 token 意味着任何 session container 可以直接读写所有租户的 secrets,绕过整个 proxy 策略层。而且没有第二道防线。

这是 moss 侧同学自己指出来的,原话是 "The single load-bearing control is the loopback bind ... it's one config line away from a serious multi-tenant breach"。这个判断是对的,而且比「要不要上 auth」本身更要紧。

3. 提议:把这条不变量焊进内核 本周做

与其靠 code review 盯住那行配置,不如让内核拒绝这个组合存在:

无 auth 只允许在 loopback 上。绑非 loopback 地址,必须开 auth(sk- token)或 mTLS —— 否则 daemon 拒绝启动。

为什么这个形状是对的

场景要改什么
moss 现状(loopback + --no-tls + 空 token)零改动。连 flag 都不用加,照常启动,多一条 WARN
有人把 bind 改成非 loopbackdaemon 直接启动失败。「一行配置就全租户裸奔」在物理上不成立了
联邦 peer(绑外网)不受影响 —— 它们本来就跑 mTLS
docker E2E / CI(非 loopback + --no-tls)需要显式加 --insecure-no-auth。它们本来就在裸奔,这个 flag 只是把事实写出来

注意我们不改 DEFAULT_BIND 的默认值(改了会打断联邦部署)。危险的不是 0.0.0.0 本身,而是「0.0.0.0 + 无 auth + 无 TLS」这个组合。所以我们让组合非法,而不是让默认值变窄。

4. 服务端的 auth,已经做完了 已 merge

moss 侧提过一个很关键的更正:「populate authToken 而不改服务端,等于什么都没做」 —— 完全正确,因为 NoAuth 根本不看那个字段。

服务端那一半我们已经做完并 merge 进 nexus-vfs main 了(PR #141 + #142)。nexusd 现在真的会校验并拒绝。

5. Tier 1 / Tier 2 — 映射到我们的机制

moss 侧提的两层方案,我们的机制都能直接承接:

moss 侧的提法我们的对应物判断
Tier 1 daemon 全局 auth token(一个共享 secret,常数时间比对) 直接用 sk- key:moss 在 NexusManager.start() 里铸一把,传给 daemon 和 NexusClient 开箱即用。代码量和「共享 secret」一样,但白送吊销/过期,以后要按 org 拆也不用换机制
Tier 2 per-namespace scoped token(签名 token 里带 allow: ["/secrets/org/{orgId}/*"],每次 RPC 校验路径前缀) OperationContext.zone_perms + 内核权限门 —— 这个接缝已经在 context 里了 同意不急。它只有在「你不完全信任 proxy 的 namespace 解析」时才值。真要上的时候接口已经在那儿了

有了第 3 节那条不变量之后,Tier 1 对 moss 就变成了可选的纵深防御(因为 loopback + 无 auth 已经合法且安全)。所以这里需要 moss 侧拍一下:是现在就上 Tier 1,还是先只要 loopback 守卫?

6. 对 moss 的具体影响 要你们确认

6.1 必须改:--bootstrap-mode 已经被删了

moss 现在传 --bootstrap-mode static(nexusManager.ts:87)。这个 flag 在 nexus 的 Phase G 已经删除 —— 现在 daemon 自己从磁盘状态推断,不需要 operator 声明。

意味着你们 pin 的是旧版 nexusd;下次 bump 到当前 release,clap 会直接报 unexpected argument 起不来。升级前必须把这个参数拿掉。

6.2 会变:root zone 现在无条件创建

凭证记录存在 raft 树里,所以 daemon 必须有一个 raft group。我们刚把「无联邦时不建 root zone」这个模式删掉了 —— 现在每次启动都会建一个 SOLO 单-voter 的 root zone。

  • 数据目录里会多出 <data_dir>/root/raft/(一个 redb 文件)
  • 多一个 10ms tick 的 transport loop(不在任何 syscall 路径上)
  • 文件 syscall 的热路径不受影响 —— / 仍然走本地 redb metastore,不进共识。root 的 raft group 是控制面,不是数据面

6.3 可能是白捡的:Readdir 是有的,SQLite 索引可以删

moss 侧的判断是「the Rust VFS has no list/readdir」,因此维护了 ~/.moss/nexus/secrets_index.db 这个 SQLite 索引。这个前提不成立。

我用真 daemon 对着 moss 的路径形状验过:

写入 /secrets/{ns}/openai.json, anthropic.json, slack.json

Readdir("/secrets/{ns}")  → is_error=False
                          → ['/secrets/{ns}/anthropic.json',
                             '/secrets/{ns}/openai.json',
                             '/secrets/{ns}/slack.json']

Readdir("/secrets")       → is_error=False
                          → ['/secrets/{ns}']

namespace 层和 key 层都能列。那个 SQLite 索引是冗余的,而且它是一个需要和 VFS 保持同步的第二 SSOT —— 删掉它是净收益。

一个 API wart:ReaddirEntry.name 返回的是全路径而不是裸文件名。迁移时注意。

6.4 一个隐含约束:namespace 里的冒号

orgNamespacePrefix() 产出的是 org:{orgId}:,路径里带冒号。VFS 会把路径映射成宿主文件名 —— Linux 上合法,Windows 上直接 InvalidFilename 写不进去。你们跑 Docker 所以今天没事,但这意味着 moss 的 nexus 数据目录不能在 Windows 宿主上落地。

7. 不归 nexus 管、但更严重的那条

moss 侧自己排的第一风险:SYS_ADMIN + seccomp:unconfined + 挂载 /var/run/docker.sock 到 moss-server(deploy/docker-compose.yml:11,17,19)。

任何在 moss-server 内取得代码执行的人,不但能碰到 loopback 的 nexus,还能控制 Docker daemon → 完整宿主机沦陷。nexus 的 auth 挡不住这个。

这条我同意确实比 nexus 这边严重得多,建议 moss 侧单独立项 —— 不在本文档范围内,但不写出来不诚实。
