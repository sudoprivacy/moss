# 指定座椅模式与氛围灯对话控制开发方案

评审基线为 `8b71ca31`。四个控制接口依据 `api-doc(3).html`，氛围灯状态查询依据 `api-doc(4).html` 的 `ep129`。开发目标是让乘客通过语音或文字控制本座位，支持直接下指令、补充参数、纠正、取消、查询和得到真实的执行回执。

## 1. 乘客体验与路由

| 乘客说 | 助手应怎样处理 | 控制请求 |
|---|---|---|
| “帮我切到办公模式” | 有有效绑定就直接执行，回复“已下发办公模式指令。” | 模式接口一次 |
| “我想眯一会儿” | 沿用舒适建议，先问是否放倒座椅。“需要”只确认已登记的放倒动作 | 建议轮零次，确认轮一次既有座椅控制 |
| “打开睡眠模式” / “把灯换成夜间效果” | 前一句切睡眠模式，后一句切呼吸灯效 | 各调用对应接口一次 |
| “氛围灯改蓝色，亮度一半” | 将颜色、亮度合并为一次设置 | 蓝色、亮度 128，一次 |
| “把灯调暗点” | 有本会话明确的近期氛围灯指代时承接该设备；灯的种类有歧义时问“要调暗阅读灯还是氛围灯？” | 澄清轮零次 |
| “恢复常亮” / “关掉氛围灯” | 已指明氛围灯时，前一句清除动态效果，后一句关闭灯位 | `scene(normal)` / `light(false)` |
| “现在是什么颜色？” / “别开灯” / “要是开睡眠模式会怎样？” | 分别走状态查询、取消或解释 | 写请求均为零 |

明确指令直接执行。将查询、否定、假设、跨座位请求和取消识别放在关键词匹配之前。“不是红色，改成蓝色”按纠正处理，“不要改成蓝色”按否定处理。语音和文字共用判定入口，语音控制只消费一次最终识别结果。回复沿用当前乘客语言，现有支持的语音语言进入同一回归集。

## 2. 四个接口的服务端契约

以下路径均从现有 `/admin-api` 基址调用。座位来自已验证的本次乘客绑定。模型工具只暴露动作和动作参数。

| 意图和 Skill | HTTP 契约 | 服务端处理 |
|---|---|---|
| `cabin_mode`，`cabin-mode-switch` | `POST /cabin/broadcast/mode-seat`，JSON 只含整数 `mode`、`aircraftNo`、`seatNo` | `office→1`、`relax→2`、`sleep→3`、`personal→4`，中文同时接受“个性/个人模式”。`title` 用于本地回复。绑定缺飞机或座位时停止下发 |
| `cabin.ceiling.color`，`cabin-hardware-control` | `POST /tcp-client/cmd/cabin/ceiling/color`，query 为 `seatNo,r,g,b,brightness` | RGB 为 0–255 整数。对话层使用 0–100% 亮度，HTTP 边界只换算一次 `round(percent × 255 / 100)`。校验后再换算，超范围请乘客重说 |
| `cabin.ceiling.light`，同一控制 Skill | `POST /tcp-client/cmd/cabin/ceiling/light`，query 为 `seatNo,on` | `on` 只接受布尔值。重新打开时调用一次 `on=true`，由控制器恢复缓存颜色亮度。关闭调用 `on=false` |
| `cabin.scene`，同一控制 Skill | `POST /tcp-client/cmd/cabin/scene`，query 为 `seatNo,preset` | 常亮、清除效果、巡航归一为 `normal`，呼吸、夜间为 `breath`，流水、登机、着陆为 `flow`。兼容既有 `cabin.scene.clear` 意图，统一发 `preset=normal`。自定义正整数按现场发布的编号和名称开放 |

3B 蓝色 50% 的出站参数应为 `seatNo=3B&r=0&g=0&b=255&brightness=128`。开关与场景接口分别操作通电状态与动态效果。“关掉呼吸效果”映射 `normal`，“把灯关掉”映射 `on=false`。若乘客要求开灯并切效果，两者能否由单个设备请求满足要经实机确认。确认前按独立动作拆分，说明先后并逐项回执。

模式接口内部负责 UE 错位发送及实际座椅的硬件联动。Moss 传乘客所坐的原始座位。办公涉及桌板打开、阅读灯和座椅回正；放松涉及桌板收起、阅读灯和座椅调整；睡眠还涉及熄屏；个性模式由后端切换 UE 模式。对一次模式请求只调用一次 `mode-seat`，由后端协调上述动作。

三个灯光写入口必须在发 HTTP 前共用座位校验。使用已绑定飞机的有效座位，规范化为控制器可识别的正排号和 A/B 列，并核对现场支持的灯位范围。仅字符格式通过不足以证明灯位有效。空值、`all`、未知排、其他列、用户指定另一座、旧绑定均停止下发，以避免后端 `obj=0` 将动作扩为全舱。Moss 只传 `seatNo`，灯位编号和硬件帧由下游生成。

## 3. 多轮补参、纠正和重复请求

服务端维护一条待完成的控制意图，存储会话、飞机、座位、绑定版本、动作、已明确的参数、缺失参数、有效期和原始请求 ID。建议沿用已有舒适建议的两分钟有效期。把灯光补参、模式澄清、既有舒适建议和订单选择放到同一个回复路由中，按上一条实际发出的问句确定“是”“不用”“一半”的归属。

1. 收到清楚且完整的请求，校验绑定、参数与本轮意图后执行。表达含糊时，先登记缺失项，再向乘客问一个具体问题。
2. 下一轮只用乘客明确提供的值和有效设备上报补齐参数。例：“把氛围灯调成暖色” → 当前亮度未知 → “亮度调到多少？” → “一半” → 下发一次暖色 50%。若乘客答“换蓝色，还是一半”，以蓝色覆盖暖色，再下发一次。
3. “算了”消费本轮待办，设备和订单写入均为零。乘客转而给出完整新指令时，以新指令为准。会话重置、换座、过期或其他座位的回复均不能消费旧待办。
4. 在发请求前用事务原子消费待办或登记请求 ID。同一请求重传或并发确认只派发一次。向下游发送后超时，将状态记为“结果未知”。此时回复“暂时无法确认是否已下发”，让乘客稍后查询。进程重启后也按未知结果处理未完成的在途写入。
5. 首期每轮最多下发一个写请求。“打开睡眠模式，再把氛围灯调蓝”先问“先切换睡眠模式，还是先调氛围灯？”颜色和亮度属于同一协议写入，可在一句话内完成。

## 4. 保留颜色、亮度与查询

完整的颜色和亮度可以直接下发。只改一项时，最多调用一次 `GET /admin-api/tcp/state/cabin/light` 读取本座灯位，保留另一项的值。服务端从乘客绑定填入必填查询参数 `aircraftNo`，并始终显式传 `seatNo`。3B 的查询形如 `?aircraftNo=B1234&seatNo=3B`。省略 `seatNo` 会查询全舱 `obj=0`，所以座位绑定缺失时停止本座查询。

收到 `code=0` 后核对 `data.aircraftNo` 和 `data.light.obj` 对应当前飞机和灯位，再按需读取 `r`、`g`、`b`、`brightness`、`preset` 和 `lightOpen`。示例中多个字段是数字字符串，需按字段解析；开关以硬件反馈 `lightOpen` 为准，`"0"` 表示关，`"1"` 表示开。颜色与亮度有值时仍可能处于关灯状态。场景按 `preset` 回复，已知编号 0、1、2 分别对应常亮、呼吸、流水。

该接口状态由硬件反馈与控制指令共同维护。VO 未声明设备更新时间，查询成功仅代表读到了当前存储值。按需读取的字段缺失、格式异常或灯位不匹配时，查询类对话回复暂时读不到，控制类对话追问缺失参数。现场用已知设置核对返回亮度与写接口 `0–255` 的对应关系，再用于换算或补参。

| 条件 | 建议对话 |
|---|---|
| 只调亮度，已有本灯位 RGB | “把氛围灯调到 40%” → 沿用原 RGB，发亮度 102 |
| 只调亮度，RGB 未知 | “调到 40%” → “氛围灯要用什么颜色？” → “蓝色” → 蓝色 40% |
| 相对调节 | “比现在暗一点”在已知亮度时按建议步长 10 个百分点调整，到边界提示已最暗或最亮。亮度未知时问“想调到百分之多少？” |
| 开关、颜色或灯效查询 | “灯开着吗？”读取 `lightOpen`，“什么颜色？”读取 RGB，“现在是呼吸灯吗？”读取 `preset`。只回答本次响应中能够确认的字段 |

## 5. 代码与发布拆分

| 交付 | 改动位置 | 完成条件 |
|---|---|---|
| 协议与保护 | `src/server/cabin/service.ts` 及共用参数定义 | 建立唯一的出站映射与座位校验，覆盖原生快路径、模型和脚本返回的动作。模式沿用广播接口鉴权，灯光沿用设备接口鉴权。HTTP、业务码、发送计数分别判断 |
| 对话承接 | `src/server/cabin/api.ts`、`store.ts`、`compactDialogue.ts` 及现有语言识别模块 | 完整表达走确定性路径，复杂表达最多一次模型意图判定。工具支持提取部分参数，统一交给服务端补齐。控制词表区分座位模式、灯效、开关与阅读灯 |
| Skill 契约 | `skills/hub/cabin-mode-switch/`、`skills/hub/cabin-hardware-control/`，按状态实测更新 `cabin-hardware-status-query/` | 同步 `SKILL.md`、脚本参数与 `CABIN_RULES.md` 摘要；调整安装版本以适配已有目录的升级机制。测试三个入口对同一意图发出相同请求，检查已启用 Skill 和座位权限 |
| 隔离验证与上线 | 现有 `src/server/cabin/__tests__/` 和 `scripts/cabin-live-smoke.ts` | 模拟接口逐轮断言请求体、次数和顺序，再在允许硬件动作的窗口进行 3B/相邻座位/UE 联调。按镜像与短规则配套发布，按同一套版本回退 |

模式同座位 20 秒限流。收到 HTTP 429 或现场确认的等价业务码时提示稍后再试，停止自动重发。HTTP 成功且业务码成功时，灯光可回复“指令已下发”。模式的 `matchedCount` 和 `sentCount` 描述 UE 客户端，如果为零应说明 UE 端未确认送达。硬件联动结果按硬件回读分别确认，避免因 UE 零送达而重复执行。日志按会话请求 ID 记录意图、座位、派发次数、参数来源、响应码、计数、耗时和结果类别。

## 6. 验收与速度门槛

| 场景 | 自动化断言或实机判据 |
|---|---|
| 四种座位模式 | 模式值为 JSON 整数 1–4，传实际座号，字段集合正确，一轮一次；UE 与实际座位分别记录结果 |
| 开灯、关灯、场景、颜色亮度 | 开关只走 light，三种灯效和旧别名只走 scene。颜色与亮度同发，0%、50%、100% 对应 0、128、255，RGB 越界和亮度 130% 要求澄清 |
| 话术区分 | “进入睡眠模式”“夜间氛围灯”“我想眯一会儿”走三种预期流程；“现在是呼吸灯吗？”只读，“别关灯”零写入 |
| 多轮与并发 | 颜色→亮度、亮度→颜色、修改、拒绝、过期、跨座回复、并发双确认、ASR 重发均核对每轮调用数；独立订单取消仍命中订单流程 |
| 状态或后端异常 | 断言 3B 查询显式传飞机编号和座位号。覆盖 `lightOpen="0"` 同时 RGB 非零、`preset="1"`、飞机或灯位不符、`light` 为空和读超时。模拟 429、业务失败、发送计数为零和写超时，核对回执及零自动重发 |
| 控制范围 | 使用 3B 与相邻座位，验证只有目标灯位变化。绑定缺失、未知座号、C 列、`all`、请求另一座均验证零写调用 |
| 对话速度 | 与 `8b71ca31 assistant-short` 用相同语料、模型、音色、3B 绑定和预热设置交替跑。分别统计完整指令、追问、状态查询、普通聊天的首字、语音准备和 UE 起播 P50/P95；区分冷启动和热态。建议每组每类至少 30 轮在隔离端点采样。初拟热态首字 P95 增量 ≤100 ms，语音准备 P95 增量 ≤200 ms，作为评审门槛。完整明确指令的模型调用为零、写调用为一次 |

首版建议采用 10 个百分点的相对调节、一轮一个写动作，并按已知含义开放自定义灯效。上述数值与性能门槛均为产品方案建议。现场联调需对照 3B 与相邻灯位的 `obj`、核实 `ep129` 的亮度单位，并核实 UE 离线时模式请求对硬件联动的回执语义。
