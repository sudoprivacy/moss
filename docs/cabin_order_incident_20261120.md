# 2026-11-20 客舱重复下单：现场对账记录

**结论：重复首先可见于 Moss 的聊天 HTTP 入口，随后被逐条执行，不是一次模型回复说了三遍。** 同一座位、平板、会话在一次语音识别返回后，7 ms 内进入四个不同的 `POST /v1/ai-chat/send`。每个请求分别调用了一次 `POST /admin-api/cabin/service-order/create` 并收到业务成功；每个请求分别确认、分别发起座位播报。三个聊天请求在约 0.2 秒内结束，另一个稍后结束。这与现场的“三次确认”吻合，但没有客户端播放/渲染记录，不能断言听到了哪三次。

## 不升级平板能查什么

**临时止损（新版 Moss）：** `cabin.serviceOrderCreateEnabled` 默认 `true`。若业务不能承担重单，在服务端配置中设为 `false` 后重启主服务：所有座位的自动创建都会被拦截，回复明确说明未下单、请联系乘务员；查单和撤单路径不变。日志记 `order.create_blocked`。这是暂停新单，不是合并重复单；已有订单不受影响。恢复设回 `true`。不想暂停正常订单就不要开启此措施。

- **现在即可核实：** 让现场导出 14:34:14 和 14:35:44 两个时间窗、该座位的订单后台记录（订单号、商品、数量、创建时刻）；按上述建单完成时间对账。现有日志没有逐笔订单号和商品，不能直接结论为“12 笔落库、12 杯可乐”。网关若有入站/转发计数，用同一时间窗对比一次转发了几次；不能只凭 Moss 指责平板的回调。
- **本次服务端改动后：** 以 `request_id` 关联 `request.accepted`、`input.ready`、`context.ready`、`conversation.ready`、`chat.ready`、`order.receipt` 和 `sse.first_text/done/error`。`asr.ready` 与 `chat.ready` 有同会话、同文本的进程内带密钥摘要 `text_ref`，仅用于观察，换进程后不同。`order.receipt` 记录品类、明细 ID、数量和是否收到订单号；只有纯数字订单 ID 才进日志。无需采集转写原文或音频。
- **读慢日志时：** `ensure.start/ready`、`socket.connected`、`prompt.submit`、`runner.first_text/completed/failed` 是 Agent 一轮内累计耗时；HTTP/SSE 阶段从请求进入起累计。相邻阶段作差，不要把累计值相加。`sse.first_text` 是 Moss 写出，不是平板显示。固定模型初始化策略在 runner 的 stderr 中看 `cabin.model_config`，不是每条暖会话都产生该日志。
- **能力边界：** 同一已发送 Agent 回合不会由 Moss 自动重放；这和上表的独立入站订单是两个问题。旧协议没有稳定操作 ID，不能按 `text_ref`、座位或时间窗自动吞单，否则会误伤乘客主动加一杯。若在客户现场不能承受重单，又无法核对账本，应先将自动下单业务转人工，不要通过重放现场请求做验收。

## 发布与验收

**数入口不要数回复。** 开启客舱日志后，已匹配的每次客舱 HTTP 请求在鉴权和读请求体之前各记一条 `type=inbound_start`（`details.phase=request.accepted`）；原有 `type=inbound` 仍是处理结束。两条不是两次请求。入口不记录正文、录音、令牌或查询串；`details.content_length` 只是请求头声明的字节数。网关若原本就带规范的 `X-Request-Id`（UUID、16–32 位十六进制或 Moss 格式），入口将它另记为 `details.upstream_request_id`；它可以被复用，不作唯一键，不覆盖 Moss 顶层 `request_id`。不要求平板新增字段。

```sh
# 在日志目录运行；第一条每行代表 Moss 实际收到一次聊天请求。
jq -c 'select(.type == "inbound_start" and .path == "/v1/ai-chat/send") | {time, request_id, upstream_request_id: .details.upstream_request_id}' cabin.jsonl
# 换成上一步的一条 Moss 请求 ID，关联入口、建单、TTS、座位下发及完成；按记录时间排序。
jq -c --arg id 'req_替换为实际ID' 'select(.request_id == $id) | {time, type, path, upstream, phase: .details.phase, status, elapsed_ms}' cabin.jsonl | jq -sc 'sort_by(.time)[]'
```

保留现有 `runtimeDefaults.type` 和 `docker.containerMode`。构建含本次修改的 ARM64 主服务镜像（包含 runner bundle 与技能），按现有流程部署；如现场持久化了旧技能副本，核对实际执行的是新版 `cabin-control.mjs`。先等在途请求结束，用新的客舱 runner 验收，不要中断正在下单的请求。检查同一请求的阶段日志及固定模型策略，不要仅看 HTTP 200。在线验收使用无副作用的对话/查询；下单验收用测试业务端点。回滚应保留日志和订单账本，且**旧镜像不识别暂停建单开关**，不能依赖它在回滚后继续保护业务。本次未修改现场配置或发布镜像。
