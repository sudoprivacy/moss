# 统一 Agent 接入标准：后续开发实施计划

日期：2026-10-22
状态：本轮 P0–P4 已完成代码与限定环境验证；详见同目录 `protocol-governance-delivery-20261022.md`。真实第三方 Provider 与生产发布不在本次完成结论内。
依据：领导提供的《统一 Agent 接入标准：协议接入批次实施、验证与 UI 说明》v0.1，以及本机三仓实际代码核对。

## 1. 这一轮交付什么

沿用现有 Dify、HTTP、OpenAI compatible、MCP、A2A 的限定协议执行能力，把外部 Agent 接入补齐为可管理、可审核、可追溯的流程：

**Moss 添加来源 → 读取并校验描述 → 生成候选 → 查看差异并审核 → 发布固定版本 → 明确切换频道 → SudoWork 选择并对话 → 查看运行证据与审计。**

来源更新只生成新候选；未获批准的内容不改变已发布版本、频道或现有任务。来源描述发生不兼容漂移时，旧版本虽然保留，也仍须通过现有运行前校验，不能保证继续调用漂移后的远端服务。

完成标准是领导方案对应条目有代码、界面和验证证据。协议批次验收与整个 Enterprise 1.1 的正式发版分开记录。

## 4. 第一批具体怎么做

### 4.1 明确数据对象

下列名称是待冻结的实验契约设计，字段在 P0 以 schema、fixture 和兼容测试确定；不能把本计划文本当成已发布 API。

| 对象 | 用途 | 需要固定的事实 |
|---|---|---|
| ExternalAgentSource | 描述一个可受控访问的 Agent 来源 | 组织、实际协议、受控连接引用、adapter version、启用状态、配置修订、最近同步摘要 |
| ExternalAgentBinding | 关联来源条目与 Moss Agent，并引用受控连接 | source ID、外部 agent ID、Moss catalog ID、连接配置修订；跨组织不能复用 |
| SyncResult | 记录每次同步尝试 | 开始/结束时间、来源修订与摘要、扫描结果、失败原因、警告；重试可增加尝试记录但不重复生成同一候选 |
| ImportCandidate | 固定本次待审核定义 | 来源快照、来源修订来源、adapter version、规范化 Manifest、与上一版差异、目标 binding、状态和审批关联 |
| ValidationReport | 保存可复核校验结果 | 结构、协议、输入输出、能力、网络与权限校验；报告绑定候选摘要、连接配置修订、适配器及校验规则版本 |
| AuditEvent | 记录谁做了什么 | actor、Org/Zone（适用时）、对象/操作、时间、关联 ID、结果和脱敏原因 |

Endpoint 和 Secret 不进入 Provider Manifest。凭据值不进入候选快照、错误详情或审计；连接可保留受控 Secret 引用。

### 4.2 统一 Catalog SPI

在现有 invoke 适配能力旁增加 discoverSources、fetchAgent、normalize、validate、getCapabilities。分别返回发现范围、来源描述、规范化候选、校验报告和机器可读能力；保留各协议现有执行限制。

“发现”是读取已配置、获准访问的来源，不扫描任意内网，也不保证仅凭一个 Dify App API Key 就枚举整个 Dify 工作区。Provider 不提供目录时，使用单应用描述或管理员提供的 Manifest 作为显式导入入口。

远端没有真实 revision 时，记录“来源未提供修订”和本次内容 digest，并明确其来源；不要把本地导入编号冒充远端版本。内容摘要可用于该情况下的去重。

### 4.3 候选生命周期与幂等

- 相同 source、外部 agent、来源修订及内容摘要重复同步，不产生重复候选或新发布版本。
- 适配器或规范化/校验规则升级需要重校验；若规范化内容或能力发生变化，形成新的待审核快照，不复用旧内容的批准。去重键须包含会影响规范化结果的处理版本。
- 同一个远端 revision 返回不同内容，作为来源冲突记录，要求人工处理，不能静默覆盖或沿用原批准。
- 来源发生变化，生成新候选；已提交/已批准候选的内容不原地改写，修改产生新的待审核内容。
- 批准与发布分开：批准只针对固定候选和校验报告；发布再次验证 actor、组织策略、来源状态和连接配置修订。
- 配置或内容变更使旧校验报告失效，须重新校验和审核。
- 发布创建固定版本；切换 stable/canary 是明确管理操作，带预期频道 revision，拒绝并发覆盖。
- 未批准候选不能进入 Task Resolution；Task 仍解析到明确的已批准版本，不直接解析 latest 或候选 ID。
- 获取来源、列表、版本等 GET 接口保持只读，不隐式批准、发布或移动频道。

UI 状态按对象拆开：候选的 draft/pending_approval/approved/rejected；版本的 published/deprecated/revoked/archived；来源的 enabled/disabled 与 available/unavailable；运行准入得到 active/不可执行。不要把这些不同维度塞成一个互斥枚举；目录显示用户可理解的组合标签和不可执行原因。

### 4.4 发布可靠性与旧数据兼容

新候选发布通过现有 RegistryReleases，保留两种 authority 的检查。涉及远端 Registry 时，固定操作标识、目标版本和摘要；响应未知先核对同一操作，不能盲目重新发布或直接切 stable。批准、版本发布、频道切换各自的结果与审计必须可追踪。

既有 binding/version/channel/task 不重建、不换 ID、不自动改变授权。采用追加表/字段及显式补建来源关联的迁移路径。历史记录缺少校验报告、adapter 或审批来源时标注未知，不能补造成功证据。

常规启动和 GET 不执行破坏性切换。任何需要切换旧 writer 的迁移必须有备份、维护步骤、旧 writer 停止检查与迁移后核验。先在脱敏副本/隔离测试数据库演练；不把当前保留的测试数据作为随意重建的对象。

兼容入口要统一走候选校验/发布控制：不能新 UI 强制审核，旧 update/onboard API 却能绕过。确需保留的旧流程必须明确定义适用的 legacy 状态，并在测试中验证不跨越新治理边界。

### 4.5 最小管理界面

Moss“专属智能体 → 外部托管”内提供：

1. 来源连接：添加/选择受控地址、凭据引用、测试、同步及结果。
2. 待审核候选：Manifest 摘要、真实协议、能力限制、校验报告、差异、提交/批准/拒绝。
3. 发布操作：从已批准候选发布版本，明确选择是否切换频道，展示完成或待核对状态。
4. 已发布 Agent：复用现有版本、频道、撤销和使用入口。

P2 再补齐全部筛选、Source 编辑/启停、全量详情和统一审计。源码实现时按现有 admin 组件结构拆分，避免继续把所有管理逻辑放进同一个弹窗文件。

## 5. 重要行为必须提前定清

| 场景 | 本计划的实现要求 |
|---|---|
| 来源不可达 | 同步结果标为不可达，保留历史候选和版本；调用仍按运行前检查决定失败或 unknown，不伪装成功 |
| 来源停用 | 阻止新候选发布和新 Task 派发；已经在远端执行的任务继续保留真实状态，不声称远端取消 |
| 来源重新启用 | 重新校验当前策略与连接；不能恢复已经撤销的版本或权限 |
| 版本撤销 | 阻止新任务，处理指向它的频道；历史结果可见；已派发任务不自动声称取消 |
| 频道回退 | 只能回到当前仍有效且未撤销的批准版本；新会话按新选择，旧会话保持原解析事实 |
| 旧版本来源发生漂移 | 保留本地不可变版本，但不跳过远端描述校验；UI 说明需重新导入 |
| 结果未知 | 请求已派发或无法证明未派发，且无法核实执行结果时保留 unknown；保留 Task/Attempt/Session 和真实原生 ID，不重发执行请求，不提供虚假取消/恢复按钮 |
| 明确未派发 | 执行前地址/权限/网络检查能够确定没有发送业务请求时，记录明确拒绝或失败，不强制归为 unknown |
| 同步重试与业务重试 | 允许受控重读元数据；这不等于允许重放 Agent 业务执行 |
| human approval 能力 | 指 Provider 运行中支持的人工介入；与 Moss 管理员审核发布分开 |
| 管理审计 | 查询按组织权限过滤，分页；Zone 无来源时明确缺失，不从浏览器自行授予；敏感内容脱敏 |

## 7. 验收清单

功能实现时逐项填写测试名称、精确提交和证据位置，不能仅填写“通过”。

| ID | 场景 | 必须观察到的结果 |
|---|---|---|
| C01 | 相同来源同步两次 | 两次尝试可追踪，同一来源快照只生成同一候选 |
| C02 | 来源更新 | 出现新候选与可读差异；旧版本、频道、历史不被覆盖 |
| C03 | revision 被复用但内容变化 | 报冲突，不能沿用批准或静默替换 |
| C04 | 未批准候选/跨组织访问 | 发布和执行均被服务端拒绝；没有越权可读证据 |
| C05 | 校验后连接/策略变化 | 旧报告不能直接批准发布；执行前再次校验权限 |
| C06 | 并发批准/发布/频道变更 | 不重复建立版本，不覆盖别人的频道更新，失败可核对 |
| C07 | 远端 Registry 发布结果未知 | 不盲目二次发布或移动频道，可按同一操作核对结果 |
| C08 | 来源不可达、停用、重新启用 | 历史保留；新调用符合准入规则；不复活已撤销权限 |
| C09 | 版本撤销/频道回退 | 撤销后新任务被拒绝；不能回退到无效版本；旧会话解析事实保留 |
| C10 | 来源修订与能力证据 | 每次执行保存实际快照；UI 不用当前 Manifest 倒填历史；旧记录缺项标未知 |
| C11 | 审计关联与脱敏 | Source→Candidate→Version→Channel→Task 可追踪，组织隔离有效且不含 Secret |
| C12 | Dify/HTTP/OpenAI/MCP/A2A | 按限定协议逐个验证；不支持的发现或运行能力明确说明，来源描述读取不执行业务 |
| C13 | 数据升级与旧客户端 | 保留旧 ID/频道/历史；GET 只读；新旧兼容策略有效；SQLite/PostgreSQL 路径按现有支持范围验证 |
| C14 | Desktop/WebUI | 共用页面状态一致；权限切换不串数据，重载不重发，协议和单轮限制清晰 |
| C15 | §12.3 十步实际浏览器流程 | 配置服务、上传 Manifest、测试、授权、审核发布、成员目录、发起任务、查看证据、revoke 后拒绝、请求派发后响应丢失且结果无法核实时 unknown 不重发，均有操作记录；另验证明确未派发的故障按拒绝/失败处理 |

C15 至少完成一次真实 Desktop 或 WebUI 流程。四种本地协议参考服务均跑自动化接入矩阵；其他 UI 组合用组件/集成覆盖，不能把这层证据写成每个平台都完成了人工验收。

Dify 可复用既有测试环境，运行时先确认可用性；真实第三方服务测试与本地 reference 测试分别标记。模型推理能力、真实商业平台互通、正式生产验收不会由一个确定性 reference 响应自动获得。

检查结果要分别列：新增测试、既有测试及 skip、类型基线、UI DOM、浏览器验收、真实 Provider、本地部署。既有 Moss 类型基线错误应单列；有失败或未执行条目时不写“全部通过”。
