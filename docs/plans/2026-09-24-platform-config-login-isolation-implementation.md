# 平台配置与登录隔离实施说明

实现分支：`codex/platform-config-login-isolation`。
Moss 基线：`origin/dev f55e42b`；Sudowork 配套基线：`origin/dev 8042fca9`。
本次只交付代码、测试和部署说明，未改动生产配置、用户密码或发布版本。

## 已实现行为

- Moss 密码登录使用 `POST /api/v1/moss/auth/login`。服务端签发 `auth_app=moss`，刷新和切组织继续保持该来源，不受组织的 Sudowork 登录方式影响。
- Sudowork 原生密码、短信、CAS 和兼容认证仍按账户实际所属组织检查策略。请求中选择的企业码只用于登录前发现，不替代账户所属组织校验。
- 组织明确选择的登录方式始终保存为组织覆盖。只有 `inherit_login_method=true` 才删除覆盖；历史组织默认值仍按已有策略解析顺序兼容。
- 原生公共配置支持 `GET /api/v1/system-config?organization_code=企业码`，未知企业码返回 404。配套客户端按服务器、企业码缓存，不让登录前发现覆盖全局运行配置；Web 转发保留企业码参数。
- 新手机注册在未提供密码时保存规范化手机号的密码哈希；兼容和原生入口均建立密码身份。注册重试保留原密码。Moss「账户安全」允许普通用户校验当前密码后自行改密，无强制首次改密。
- 原生 CAS 票据登录、回调与一次性交换独立于 `sudoworkCompatibility.enabled`。该开关继续控制旧协议按 Host 分发，不作为原生短信/CAS 的总开关。

## 平台配置

入口：Moss「系统 → 平台配置」，`/admin/settings/platform-config`。
只允许真实角色为 `super_admin` 的用户访问；普通组织管理员即使拥有 `*` scope 也不能访问。旧服务器凭据 API 同步收紧到超管。

五组配置：腾讯短信、Sudorouter、富友支付、Dify、QMS。普通字段存全局 `platform_integration_settings`；密钥存 Nexus `moss:platform-config` 的不可变版本，数据库只存引用。Dify 企业资源、Router 个人模型 Token、订单和 QMS 企业访问权限仍按原有归属管理。

API：

- `GET /api/v1/platform-config`：脱敏配置、版本、来源、冲突和各实例生效状态。
- `PUT /api/v1/platform-config/:provider`：`expectedVersion` + `config` + `secrets`；首次保存即接管。
- `POST /api/v1/platform-config/:provider/check`：字段完整性、候选配置和凭据读取检查。
- 密钥字段不提交表示保留，字符串表示替换，`null` 表示清除。脱敏占位符不能作为密钥写入。

未接管时沿用部署来源；接管后使用数据库和 Nexus 版本，旧环境变量不再覆盖。旧组织设置的短信/支付基础设施写入口返回迁移提示；旧凭据入口也不能覆盖已接管字段。

**保存后需重启 Moss 才生效。** 页面区分保存版本和本实例加载版本，并显示其他实例心跳。保存先暂存并校验凭据，再事务提交配置；失败不会发布半套配置。失败时留下的无引用凭据版本不参与运行时读取，可在后续运维清理。

配置检查不会发送短信、创建支付单、退款或主动连接生产数据库；检查通过不代表腾讯余额/模板、Router 权限或第三方网络已通过真实调用验收。

短信配置检查和发送读取同一份生效通道，支持旧 `phoneAuth.tencent` 和 vault 引用，无须打开旧兼容开关，不再要求未使用的 `signId`。Secret ID/Key 从同一来源成对读取，避免拼接不同账户。已启用兼容短信的部署也映射到同一份原生短信配置。

Router 两套管理 Token 消费者共用接管后的 URL、管理员 ID、Token 和超时；原生客户端的默认 Router 服务/模型发现地址同步应用。其他组织自定义模型服务和个人模型凭据保留。

富友停止新支付时保留历史支付处理所需密钥；仍需 Router 可用才能完成额度发放。已有商户身份、环境或密钥不允许直接改写。QMS 既有加解密密钥同样禁止覆盖或清除。**本次未实现在线密钥轮换/历史密文重加密；需要这些变更时须另行实施迁移，不能在普通保存中绕过。**

## 历史无密码用户

平台配置页提供“预览待处理用户 → 补齐”。也可使用：

1. `GET /api/v1/platform-config/password-migration` 获取数量、用户 ID、跳过原因及指纹。
2. `POST` 同一路径，提交 `{ "fingerprint": "预览返回的值" }`。

仅处理已启用的普通用户、可信 `phone/sudowork` 身份且没有密码的记录。已有密码、管理员、禁用用户、缺失或冲突手机身份不重置。预览集合变化时拒绝执行并要求重新预览；重复执行不覆盖已设置的密码。

手机号作为初始密码是本次明确选定的产品行为，用户主动修改前仍具有可猜测风险；本次没有加入额外激活或强制改密。

## 发布顺序与验收

1. 备份数据库及现有部署配置/Nexus 凭据；保存旧版本发布包。
2. 先部署带 Moss 专属密码入口的服务端与管理端，清理旧管理端静态资源缓存。旧的、未携带应用来源的密码会话需重新登录。
3. 发布 Sudowork 配套分支，使企业码发现、缓存及 CAS 登录入口同步更新。旧客户端请求仍兼容，但不能代表其登录页已经支持组织选择。
4. 超管逐组核对导入值和冲突，保存并接管；安排各实例重启，检查加载版本。
5. 用指定测试账号验证组织 A/B 登录方式互不影响、Moss 始终可密码登录、注册默认密码与自行改密；按需要预览并补齐历史无密码用户。
6. 在明确的测试手机号/测试商户条件下另做短信和支付联调。本次本地验证没有调用这些生产服务。

回滚代码时仍需保留新凭据版本和已修改的用户密码。不要用旧用户表覆盖用户上线后自行设置的新密码。接管后的配置不自动回退到旧 env；回滚材料应由管理员按版本核对恢复。
