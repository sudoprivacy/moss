# 组织模型管理补充方案：成员限额、个人用量与后台充值

日期：2026-10-08
状态：已实施并完成回归，2026-10-08。真实 SudoRouter 已联调；富友保持协议模拟。限额切回有限的接口限制与最终适配见 3.2。
范围：Moss、Sudowork；不修改 SudoRouter/new-api、sudostack、已停止维护的 sudowork-server。

## 1. 已确定的产品规则

一个组织对应一个 SudoRouter 账户。默认服务 Key、组织管理员 Key、普通成员 Key 均属于该账户，消费共享组织余额。成员限额是消费限制，不是个人余额。

本轮补齐四项功能：

1. 已创建成员可以切换“限额／不限额”。
2. Moss 用户列表可以查看指定成员的 Key 状态、累计用量和消费明细。
3. Moss 超级管理员可以直接给组织账户后台充值，不强制绑定支付订单。
4. Sudowork 用户中心对所有角色统一展示本人用量；组织管理员也只能在这里看到自己 Key 的使用情况。

全面使用美元金额，不恢复积分。后台充值增加组织余额；成员限额调整不增加或减少组织余额。组织余额耗尽时，即使成员不限额也不能继续使用。

## 2. 页面与权限

| 入口 | 普通成员 | 组织管理员 | Moss 超级管理员 |
| --- | --- | --- | --- |
| Sudowork 用户中心 | 本人限额、Key 状态和消费明细 | 同样只显示本人 | 若存在本人 Key，也只按本人查询；不能因角色扩大范围 |
| Sudowork 组织充值中心 | 不可访问 | 组织余额、富友充值、组织充值记录 | 超管身份本身不授予客户端付款权限 |
| Moss 用户列表：限额管理、模型使用情况 | 不可访问 | 当前组织成员 | 当前所选组织成员 |
| Moss 账务管理：组织充值记录 | 不可访问 | 当前组织 | 当前所选组织 |
| Moss 账务管理：后台充值、人工核对结果登记 | 不可访问 | 不可操作 | 可操作当前所选组织 |

角色、组织、成员及账户归属由服务端核验。前端不传任意 Router 账户 ID、Token ID 或 Token 名称决定查询和充值目标。

组织整体余额和累计消费保留在 Moss 的组织模型账户管理中；Sudowork 组织充值中心保留组织余额和账务。用户中心不再显示组织余额、组织累计消费或其他成员日志，也不包含默认服务 Key 的消费。

## 3. 成员限额管理

### 3.1 现状与目标

实施前创建成员可指定有限或不限额，创建后只能增减有限 Key 的剩余额度；本轮已补模式切换入口。

Moss 用户列表保留“模型限额与 Key”，增加模式选择与明确的保存操作：

| 操作 | 用户填写 | 保存后的含义 |
| --- | --- | --- |
| 有限 → 不限额 | 选择“不限额” | 此成员不设独立消费上限，仍受组织余额约束 |
| 不限额 → 有限 | 选择“限额”，填写剩余可用 USD | 从切换成功时起可继续消费指定金额 |
| 有限 → 调整剩余限额 | 填写增加或减少的 USD | 沿用现有增量调整，不重新计算历史消费 |

切回有限时不默认恢复历史剩余额度。允许设为 $0，含义为无可用限额。累计消费保留，不因切换清零；Key、Token ID 和名称不更换。切换不能自动启用已停用 Key，也不能绕过用户或组织停用。

新组织默认成员限额、后台创建成员时的默认/有限/不限额选择、邀请码注册继承组织默认的规则继续保留。修改组织默认只影响后续成员。

### 3.2 SudoRouter 依赖

已实测并复用 `PUT /api/user/token/quota`，但其实际行为有一个必须单独处理的分支：

- `unlimited_quota: true` 保留历史剩余额度，不清空累计消费，也不改变停用状态。
- `unlimited_quota: false` 且 `delta_quota != 0`：无论原模式如何，都是**增量**。
- `unlimited_quota: false` 且 `delta_quota == 0`：将剩余额度清零，**不是零增量的无操作**。
- 不限额消费后的 `remain_quota` 可为负；推理返回后，预扣、退款和消费统计可能延迟结算。

最终实现从不限额切回有限时，先用零值切换并清零，再用正增量加上明确填写的新预算；$0 只执行第一步。正历史余额、负历史余额以及恰好等于新预算的历史余额均不参与新预算计算。Key、累计用量和管理启停状态不变。清零之后结算的在途消费继续正常扣减，不通过读取后覆盖余额抹掉消费。

这是对原单次原子切换设想的实施调整：**现有接口不能将“模式切换 + 指定绝对剩余限额”作为一个原子请求完成。** 两步之间可能短暂为零限额并拒绝新模型调用；两步均在 Moss 同一成员互斥锁和已持久化操作内执行。任一步结果未知，或第一步成功而第二步失败，整个操作标记待核对，禁止重新发送及后续额度增减。停用 Key 不会自动启用。已成功命令重放不会覆盖后续命令。

后续若要求完全消除短暂零限额及部分成功窗口，SudoRouter 只需增强现有接口：原子设置 `unlimited_quota` 和绝对剩余额度，并明确与在途结算的关系及请求幂等语义。当前实现不声称具备上游未提供的原子能力；不新增账户充值、日志接口，也不替换成员 Key。

## 4. 个人模型使用情况

### 4.1 Sudowork 用户中心

实施前 `ModelAccountPanel` 顶部累计费用已来自 `account.member`；组织管理员还会看到组织余额，日志标题变成“组织用量”。Moss 的 `logs()` 也会因 `can_manage` 而取消 Token 过滤，因此问题同时涉及前后端。

目标行为：

- 所有人统一显示“我的模型使用情况”：本人剩余限额/不限额、本人累计费用、本人 Key 状态和本人消费明细。
- `GET /api/v1/model-account/logs` 对任何角色都只查询当前登录成员的 Key；管理员身份不改变范围。
- 没有本人 Key 时显示“模型凭据尚未就绪”和空明细，不回退到默认服务 Key 或组织日志。
- 用户中心只使用现有账户响应中的 `member` 数据。现有账户接口的组织字段仍服务于管理员充值页面及 Moss 管理页，不要求新增一个个人概览接口。
- 切换登录账号时清空旧明细与页码，缓存按用户/组织身份隔离，旧请求返回不能覆盖新账号数据。

例如：管理员消费 $1、成员 A 消费 $2、默认服务 Key 消费 $0.50，组织共消费 $3.50。管理员用户中心显示 $1 和管理员自己的明细；组织账户管理显示 $3.50。

### 4.2 Moss 用户列表

在操作菜单中增加“模型使用情况”，打开详情抽屉：

- Key 信息：Token ID、名称、掩码、启停和有效状态。
- 用量概览：限额模式、剩余限额、累计消费 USD。
- 分页明细：时间、模型、输入 Token 数、输出 Token 数、费用 USD、耗时（上游有值时展示）。

概览使用 Router Token 的累计值；明细使用日志接口。不把当前页合计伪装成累计用量，不承诺未验证的日期筛选、按模型汇总或全量导出。

Moss 按所选成员的可信绑定调用 `GET /api/log/query`，设置组织 `user_id`、`type=consumption` 及该成员的 `api_key_name`。名称缺失、重复或绑定错误时返回明确错误，不扩大为全组织查询。完整 Key、Router 管理凭据不下发到页面。

个人入口与管理入口复用查询逻辑，但授权分开：个人入口固定登录人，管理入口核验操作者与目标成员的组织。供应方原始日志 ID 未提供，不将展示 ID 当成可核账的唯一凭证。

## 5. 独立后台充值

### 5.1 入口与输入

Moss「运营中心 → 账务管理 → 组织充值」增加“后台充值”，仅超级管理员可用。

| 字段 | 规则 |
| --- | --- |
| 目标组织、Router 账户 | 根据当前所选组织展示并由服务端锁定，不接受客户端指定其他账户 |
| 充值金额（USD） | 必填正数，最多两位小数；建议首版 $0.01–$10000.00，与在线充值的单笔上限一致 |
| 充值原因 | 必填，记录业务原因或异常情况 |
| 关联支付订单 | 可选；普通后台充值不需要订单，异常补充可选择当前组织订单 |

提交前展示组织、账户、金额供操作者确认。直接按填写金额增加组织余额，不使用富友网关，不套用支付套餐赠额，也不改成员限额。

需要给原 $10+$1 订单完整补充时，后台充值金额填 $11；若选择关联订单，可展示原购买额、赠额和既有人工补充额供参考，最终提交金额必须明确可见。

### 5.2 资金记录

后台充值使用独立记录，不伪造富友支付订单。记录充值单号、固定组织/Router 账户、USD 与换算 quota、操作者、原因、可选原订单、请求标识、状态及到账时间。

沿用 `PUT /api/user/quota` 增加组织账户额度。每次操作先持久化，所有尝试可追溯；同一提交标识重复请求只返回已有结果，相同标识不同金额或组织返回冲突。

记录状态为：待处理 → 处理中 → 已到账 / 明确失败 / 结果待核对。超时、连接中断、写入成功但本地保存失败均不能直接显示为“未到账”，也不能自动换标识重发。

“账务管理 → 组织充值”统一展示两种来源，并可按来源筛选：

| 来源 | 金额 | 付款信息 | 责任人 |
| --- | --- | --- | --- |
| 富友在线充值 | 购买 USD、赠送 USD、实际订单应付 CNY | 支付方式、付款状态和时间 | 付款人 |
| 后台充值 | 管理员填写的 USD | 显示“无需支付”，没有虚构的 CNY 收款或支付时间 | 操作人及充值原因 |

两类记录各自显示到账状态。历史个人账务继续单独保留原始数据，不参与组织充值统计。Sudowork 组织充值中心同步展示后台充值记录，使用相同来源区分；普通成员仍不可查看组织账务。

### 5.3 根据异常订单人工补充

产品采用人工判断后直接后台充值，不强制自动补单。查看订单异常不产生任何资金写入，订单异常本身也不是“远端未到账”的证明。

关联异常订单时必须做到：

1. 原富友付款事实和原 Router 入账尝试记录保持不变。另记人工补充金额及处理原因，不把后台充值改写成原富友订单正常到账。
2. 开始关联补充前，在原订单详情选择“转人工处理”，持久化关闭自动加额并记录操作者。回调、查单、重试等入口统一检查该模式，后续合法回调仅更新付款事实，不再自动加额。关联后台充值提交时在同一处理锁内再次校验。
3. 原加额请求仍在途时不能开始关联补充。结果未知的原请求先人工核对并登记结论，再决定是否补充；本地锁无法撤销已发往 Router 的请求。
4. 后台充值失败或结果未知时保留人工处理模式，不自动恢复原单加额。需要继续核对，不通过重复点“充值”解决。
5. 展示关联后台充值记录及累计人工补充金额。关联不等于足额结清，部分补充不能自动标为全部到账；原单保留独立的人工处理状态。

原订单详情提供受限的“登记原入账结果”：已到账只修复本地结果、不发钱；确认未执行后才允许关联补充；无法确认则保持待核对。转人工与登记结论不能绕过仍在途的请求。核对依据和原因必填，不通过通用编辑订单字段完成。

原订单人工处理状态区分“待核对、可补充、部分补充、处理完成”。累计人工补充额仅统计已确认到账的后台充值；失败金额不计入，未知金额单列且阻止为同一缺口再次补充。每笔独立后台充值在组织统计中只计一次，原支付金额是收款事实，不再将原单应到账额与人工补充额重复计作 Router 实际入账。

全部在途/未知操作已核清后，由超级管理员在原订单详情登记“处理完成”。页面展示原应到账额、已确认原入账额、人工累计到账额和差额；金额仍不足时保留“部分补充”，不能显示足额到账。超额或其他差异需记录人工核查结论，不自动抹平。结案后原订单仍保持禁止自动加额，晚到回调不能重新打开自动发放。

不关联订单的后台充值是独立组织加额，不会改变任何支付订单，也无法防止原异常订单之后继续自动入账。若用于异常订单补充，应使用关联入口完成上述处理。

### 5.4 后台充值结果核对

结果未知时提供超级管理员“登记核对结果”：

- 确认 Router 已到账：只补齐本地状态，登记核对依据，不再调用加额。
- 确认原请求没有执行：登记失败/未执行结论，随后才能人工发起新的到账尝试，保留前次记录。
- 无法确认：维持待核对，禁止重复发送该笔充值。

再次尝试采用“同一后台充值单下新增到账尝试”。仅明确未执行/已核实未执行的记录允许点“重新尝试”；金额、组织、账户保持原值，使用新的尝试标识，保留前次请求与核对记录。服务端原子校验状态并保证每单最多一个活动尝试；同一重试标识重放只返回已有尝试。充值单只占一条业务记录，成功金额不因尝试次数重复统计。不得把未知充值简单复制为新单重发。

不能只比较当前余额推断到账：同账户存在并发消费和其他充值。Router 的 `comment` 只用于追溯，不等于远端幂等凭据；本轮不承诺无人值守恢复未知资金操作。

## 6. Moss 接口建议

接口命名为实施建议；不新增 SudoRouter 充值或日志接口。所有写操作使用稳定 `Idempotency-Key`，个人日志不接受客户端选人。

| 接口 | 变更 |
| --- | --- |
| `GET /api/v1/model-account` | 继续返回本人 `member`；现有组织字段仅由组织页面使用 |
| `GET /api/v1/model-account/logs` | 修改为所有角色固定本人日志；更新旧“管理员返回组织日志”的测试和文档 |
| `POST /api/v1/model-account/members/{userId}/limit` | 保留现有有限 Key 的增加/减少限额 |
| `PATCH /api/v1/model-account/members/{userId}/limit-mode` | 新增模式切换，有限模式明确指定剩余可用 USD |
| `GET /api/v1/model-account/members/{userId}/usage` | 新增管理端指定成员概览与分页明细 |
| `POST /api/v1/model-billing/admin/credits` | 新增直接后台充值，可选关联已转人工且允许补充的异常订单 |
| `POST /api/v1/model-billing/admin/credits/{creditNo}/resolve` | 新增登记后台充值核对结果，非通用任意订单状态修改 |
| `POST /api/v1/model-billing/admin/credits/{creditNo}/retry` | 明确未执行后，在同一后台充值单下发起新尝试 |
| `POST /api/v1/model-billing/admin/orders/{orderNo}/resolution` | 原支付订单转人工、登记原入账结果或结案；各动作分别检查前置状态，不直接加额 |
| `GET /api/v1/model-billing/admin/orders` | 扩展来源区分、后台充值记录和关联处理信息 |
| `GET /api/v1/model-billing/orders` | 组织管理员充值中心增加后台充值记录；在线支付动作仍只适用于富友订单 |

模式切换请求示例：

```json
{"unlimited": true}
```

```json
{"unlimited": false, "remaining_limit_usd": "5.00"}
```

后台充值请求示例（组织取当前可信上下文）：

```json
{
  "amount_usd": "11.00",
  "reason": "人工核对后补充组织额度",
  "related_order_no": null
}
```

关联旧单时，服务端再次验证同组织和处理状态。来源字段不得由普通客户端自由指定，后台充值路由固定记录为后台来源。关联处理状态、补充记录和操作状态的变更要使用事务及持久化互斥，不能只靠按钮禁用防重。

## 7. 实施范围与顺序

| 仓库 | 涉及模块 |
| --- | --- |
| Moss | `organizationBillingService/Routes` 的个人与管理用量、限额模式；`organizationRouterAdapter` 的模式切换适配；后台充值数据与处理服务；现有回调/查单入口的人工处理检查；用户列表、Key 弹窗、成员用量抽屉、账务页 |
| Sudowork | `settings/model-account` 用户中心、缓存和日志分页；`settings/recharge` 后台充值来源展示；相关类型、国际化及测试 |
| SudoRouter | 复用已有账户充值、Token 查询和日志接口；联调确认限额模式切换的现有能力，暂不要求新增接口 |

实施顺序：先修正个人用量范围并补指定成员查看；并行准备限额模式的真实接口验证；然后实现后台充值、来源展示和异常关联处理，最后做资金异常与权限回归。这里的并行指可独立安排的开发工作，不代表已启动实施。

本轮不修改开户密码规则、API Key 下发路径、组织共享资金模型，不新增每月重置限额、额度申请、后台扣款或组织退款。

## 8. 验收场景

1. 管理员、两名成员和默认服务 Key 各产生消费；每个人用户中心都只显示本人费用和日志，管理员也不显示组织余额。组织管理页仍显示正确组织总额。

### 核对接口参数

`POST /api/v1/model-billing/admin/orders/{orderNo}/resolution` 的 `action` 为 `takeover`、`original_result` 或 `close`；均要求 `evidence`。登记确定的原入账结果还需 `outcome: credited | not_executed` 和 `confirm_request_finished: true`，由操作者确认原请求已结束且不会继续执行。`unknown` 维持待核对。

`POST /api/v1/model-billing/admin/credits/{creditNo}/resolve` 使用相同 `outcome`、`evidence` 和完成确认字段。核对已到账只修复记录，核对未执行后可在同一充值单上 `/retry` 新建尝试。仍在本进程执行的请求由共享锁隔离；进程重启遗留的发送中记录必须人工核对，不能按超时自动判断未执行。
