| 事项 | 用户决定与本期处理 |

## 2. Token 过滤与旧日志入口的区别

**按 Token 过滤可以解决正常查询结果的归属，但不能单独解决旧入口的访问问题。**

精简后的新增 N01 是 Key 列表/状态/限额查询，token_id 用来筛选 Key 记录，并非日志接口。基本消费明细复用管理员 GET /api/log/，由 Moss 按可信 user_id/token_id 映射、过滤后返回成员；不能直接透传组织日志和组织总条数。

当前旧 GET /api/v1/logs/ 由成员真实 Key 鉴权，但控制器只强制 opt.UserID，没有强制当前 Token ID。A、B 的 Key 都属于组织账户 1001 时，A 仍可直接请求旧入口获得账户 1001 下其他成员的日志记录。这里指已核实的日志记录范围，不推断一定包含完整对话。

依据：[TokenAuth 路由](/Users/yobach/VSCodeProject/new-api/router/api-router-v1.go:12)、[仅限定 UserID 的控制器](/Users/yobach/VSCodeProject/new-api/controller/v1/logs.go:85)。本轮已重新读取源码；历史隔离验证见主方案第 13 节。

即使另增一个按当前 Token 强制过滤的日志接口，旧入口仍然存在。因此“旧接口行为完全不变、真实成员 Key 可直连旧入口、成员日志严格隔离”目前不能同时满足。共享公司资金的决定不等于允许成员互查日志。实施时仍需解决这一访问边界并验证；本次不默认修改旧接口、不默认采用代理，也不自动追加第四个接口。它是严格日志隔离承诺的未解决条件，不是要求再建一套日志系统。

## 3. 创建与限额的具体规则

- 有权限的后台操作者创建组织时设置初始额度（USD），对应组织 Router User 的资金；组织默认 Key 的服务限额、成员限额分别管理。
- 沿用现有初始补额规则：Router 已有赠额计入初始目标，仅补不足，超过目标不自动扣回。补额复用 PUT /api/user/quota，只在新账户尚未开放消费时计算并固化一次；登录、建成员和任务恢复不按当前余额重新补齐，未知结果进入核对。
- 后台建成员可选有限额或不限额；未指定时使用组织默认设置。邀请码注册只能继承服务端配置的默认设置，注册者不能自行选择更高限额或不限额。
- 默认设置只影响之后创建的成员，不改已有成员；组织管理员作为成员使用自己的 Key，不使用默认服务 Key 绕过限额。
- 已创建的有限额成员支持追加/降低剩余限额及停用/恢复；运行中切换有限/不限额、周期重置仍不在首版。不限额成员同样受组织余额约束。

组织初始额度示例：目标 $100、Router 已赠送 $10，只补 $90；若已赠送 $120，保留实际 $120。组织服务 Key 仍须具备可用配置，不能把零限额的普通推理 Key 当作只读模型目录凭据。

## 4. 保留的实现边界与验证

保持现有支付设计不代表旧接口已具备远端幂等：已确认到账的订单不重复 PUT，远端结果未知须核对后处理，不能盲目补发。这是已有方案的实现边界，本次不新增支付产品能力。订单固定组织收款绑定，历史个人订单保持原归属。

额度不足提示可以统一，但开通中、Key 停用、网络失败等继续保留各自状态，不能把所有错误报成额度不足。余额判断使用原始 quota；当前预扣与最终结算不构成绝不超额保证，产品不额外承诺硬预算。

首版验证重点：组织初始额度只发一次；后台有限/不限额与邀请默认值有效；两成员消费归属和共享余额正确；普通成员不能充值；额度不足提示符合已确认方式；重复支付通知不重发已到账资金；旧日志入口访问边界实际得到解决；USD 迁移不重复注资。

Key 高级管理界面、泄露后的轮换恢复增强、最后管理员交接规则的进一步核查、支付 SLA、价格展示扩展和试点指标仅保留为后续候选，不因本评审变为首版新增要求。现有权限、停用能力及已确认支付处理仍按主方案执行。
