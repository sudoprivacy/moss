# 平台公共配置与 Moss / Sudowork 登录隔离方案

日期：2026-09-23；2026-09-24 修订并实施于开发分支。实际交付、限制和发布步骤见 [实施说明](2026-09-24-platform-config-login-isolation-implementation.md)。尚未部署生产；以下保留方案设计及原始问题核查。

建议：新增「平台配置」页面，复用现有全局配置表和 Nexus 凭据服务；短信校验与发送共用同一份有效配置；Moss 登录固定为账户密码，Sudowork 登录策略按组织独立配置。按用户 2026-09-24 明确要求，Sudowork 注册用户默认密码为手机号，可直接登录 Moss 后自行修改，不加入强制激活、二次短信验证或强制首次改密。

## 1. 已核实的问题

### 1.1 生产短信保存失败的原因

本轮只读 SSH 核查：生产 `moss-server` 正常运行，版本为 `server-v0.1.40-migration.20260923`。实际 `/home/ubuntu/.moss/server/server.json` 中：

- `phoneAuth.enabled=true`，`phoneAuth.tencent` 下已有腾讯短信应用、签名、模板、地域和旧 vault 密钥引用。
- `sudoworkCompatibility.enabled=false`，没有配置该分支的短信参数。
- `platform_integration_settings` 当前为空。

现在发送和后台保存走了不同路径：

| 环节 | 当前读取来源 |
|---|---|
| 原生短信发送，当前 Sudowork 客户端也使用 | `phoneAuth.tencent`；密钥从 `server.sms-secret-*` 或旧 vault 引用读取 |
| 后台切换短信登录的校验 | `sudowork.sms` 平台记录或 `sudoworkCompatibility.sms`，并要求兼容模式启用 |
| 兼容短信发送 | 单独的 `SmsVerificationService`，依赖兼容 Redis 和另一套腾讯密钥 |

所以“配置文件里有腾讯短信”属实，但目前保存校验没有使用正在提供短信服务的那套配置。不能通过去掉校验来解决，也不应为此直接开启旧兼容模式；后者还要求 trusted hosts、JWT、Redis，并可能改变路由分发。

另有两个相关缺陷：`signId` 被强制要求，但现有腾讯 SDK 发送参数中并未使用它；同次提交短信参数与登录方式时，当前实现先检查旧配置再解析新配置。

核查范围：确认了配置路径及确定性的拒绝条件，没有实际发送短信，因此不将此结论等同于腾讯云账户、模板和余额已通过发送验证。

### 1.2 Moss 登录方式被影响的原因

`AuthService.issueTokenFromPassword()`、公共 token 签发和刷新都检查组织登录策略。组织切到短信或 CAS 后，Moss 管理端即使保留密码表单，也会被后端拒绝。只修改前端无法修好，刷新、切组织和会话续期也必须一起处理。

此外，当前原生 `/api/v1/system-config` 由 `server.json.systemConfig` 构建，后台策略从数据库读取；公开登录配置与实际校验也存在来源分叉。

### 1.3 公共配置已有基础，但入口和运行时不统一

- `platform_integration_settings` 本来就是没有 `org_id` 的全局表，短信和支付基础设施已经部分使用它。
- `moss:config` Nexus 命名空间已存放全局敏感配置，服务器凭证页已支持脱敏编辑。
- Router 当前生产的 URL、管理员 ID、Token 等来自独立 `sudorouter.env`；环境变量优先，直接在页面保存可能仍被旧环境变量覆盖。
- Router 有 `server.sudorouter-admin-token` 与 `server.sudorouter-api-token` 两套消费者；短信也有两套密钥名，不能只合并页面标签。
- 服务器凭证 API 目前仅检查 `admin:settings`，而普通组织管理员也有 `*` scope。平台公共密钥应增加真实平台超级管理员校验，旧写入口也要同步收口。

### 1.4 手机号默认密码目前没有实现

原生 `registerUserFromPhone()` 和兼容 `registerByVerifiedPhone()` 的短信注册都没有自动传入密码，统一用户创建器因此写入空 `password_hash`。不能通过放开密码登录策略就让这些用户使用手机号登录。

## 2. 页面与配置范围

新增「系统管理 → 平台配置」，建议路由 `/settings/platform-config`，仅平台超级管理员可见、可编辑，不受当前选中组织影响。沿用服务器凭证的组件和存储能力，将相关平台字段集中到这里；旧凭证页保留其他服务器凭证，对已迁移的平台分组提供跳转，避免双入口独立编辑。

| 平台分组 | 普通配置 | 敏感配置 |
|---|---|---|
| 腾讯短信 | 启用、SdkAppId、签名、模板、地域、模板参数、验证码有效期和发送限制 | SecretId、SecretKey |
| Sudorouter | 管理 API 根地址、AdminUserId、模型服务地址、模型列表地址、超时 | 平台管理 Token |
| 富友支付 | 启用、测试/生产环境、商户号、支付/退款网关、超时、回调地址 | 商户私钥、平台公钥及其版本 |
| Dify | 服务地址、超时、全局集成开关 | System Token、开户 Secret、SSO Secret |
| QMS | 启用、采集/加密策略、批量与保留周期、通知渠道配置 | PostgreSQL/Redis 连接凭据、API Key、加解密密钥、Webhook/SMTP 凭据 |

QMS 在当前代码里包含进程内运行时、数据库和队列，不能只设计成一个 URL + Token 的外部接口表单。

每组提供保存、配置检查，以及已保存/当前生效状态；显示来源、缺失项和是否需要重启。密钥只显示“已设置”，提交时明确区分保留、替换、清除。

“检查配置”只做字段、凭据读取和可用的只读连接检查。实际测试短信是单独的手动操作；支付检查不创建订单或退款。

**全局共享的边界：**共享平台服务地址和平台管理凭据。Dify 企业空间/应用/知识库绑定及其业务密钥，Router 用户/组织账户和个人模型 Token，订单/钱包、QMS 企业数据与访问权限，继续保留原有归属。把这些一起全局化会造成跨组织数据或额度混用。

初始额度、充值审批方式、组织是否启用产品改进等是业务策略，保留在客户端/组织策略中；平台页仅引用必要的部署默认值，明确 Router quota 单位，避免与积分混用。

## 3. 存储、优先级与生效规则

### 3.1 复用存储，统一解析

普通配置继续存入 `platform_integration_settings`，按 `sms.tencent`、`sudorouter`、`payment.fuiou`、`dify`、`qms` 分组；增加配置版本和生效状态。已有 `sudowork.sms` / `sudowork.billing` 作为迁移来源。

敏感内容继续存 Nexus，普通配置只引用对应凭据版本。新增统一的 `PlatformConfigService`，负责解析、校验、来源标记和运行时配置。后台校验、实际 SDK、旧/新业务适配器、公开配置投影都通过它读取。

### 3.2 优先级采用明确接管

- 尚未接管的分组：保持现有来源及优先级，展示有效来源，避免上线自动换账号。
- 超管在页面完成“导入现有配置并接管”后：该组数据库配置 + Nexus 凭据成为唯一来源，旧环境变量和文件不再覆盖它。
- 接管后清空字段表示明确清空，不偷偷回退到旧密钥。回退旧来源必须是显式、可审计的操作。
- 基础设施启动必需的数据库位置、Nexus 引导连接等仍放部署配置，避免配置服务依赖自身尚未读取的配置。

导入只在服务端读取现有有效值，页面看到脱敏预览。SecretId/SecretKey 成对处理；Router 管理员 ID、Token、地址作为同一配置组验证。两套历史值不一致时显示冲突，不自动拼接或任选。

### 3.3 不把“保存成功”等同于“已经生效”

第一版平台集成配置统一按“保存后受控重启生效”交付，保留现有已经即时生效的非迁移凭据功能。登录策略本身实时生效，但启用短信前要求当前运行时确实就绪。

原因：Router、Dify、兼容短信和 QMS 多处在启动时捕获配置，单纯修改内存字段不会重建这些实例。第一版不承诺未经实现的热更新。

保存时先验证候选配置并写入新凭据版本，再提交配置版本引用；失败保持上一生效版本。普通配置与 Nexus 不共享事务，必须处理部分失败，不能留下半套可见配置。多实例显示各实例加载版本；未全部应用时标记“待生效”。

支付商户/验签密钥轮换必须保留在途订单对应版本，并支持旧订单回调验签和退款；不能删除旧密钥后再发现订单无法处理。

QMS 首轮接管原样保留现有密钥。仍用于解密历史数据的密钥版本不得直接清除；后续轮换需按数据密钥版本读取，或先完成可验证的数据重加密。若历史密文没有版本标记，先补充兼容读取机制，再允许轮换。

## 4. 短信修复方案

1. 先将“短信可用性”提取为公共服务，读取实际运行的短信发送通道。兼容模式关闭不再自动等同于短信不可用。
2. 兼容现有 `phoneAuth.tencent` 参数及 vault 引用，允许平台配置接管；保留原有模板参数映射、验证码有效期和限流行为。
3. 把配置是否完整、凭据是否可读、运行时是否已加载分别报告；失败提示具体原因，不再统一提示“短信服务未配置”。
4. 腾讯短信所需字段以实际调用为准，取消当前未使用的 `signId` 硬性门槛。
5. 页面把平台短信配置与 Sudowork 登录策略分开保存。旧接口若允许同次修改，则先合并候选配置再校验，并明确尚待重启的状态。
6. 两种短信入口共用相同的服务配置解析；验证码存储、限流及发送服务不再隐含依赖旧协议兼容开关。

## 5. Moss 与 Sudowork 登录隔离

每个组织单独保存 Sudowork 登录方式，组织 A 切换不会写入组织 B 或平台默认。组织明确选择后持久化为组织覆盖，即使当前值恰好等于平台默认，也不能因自动去除同值而重新变成继承。只有用户主动选择“跟随平台默认”才删除覆盖。平台短信等公共配置共享，不影响该策略的组织隔离。

可在短信、密码、CAS 之间切换，但目标方式必须就绪：短信要求公共通道可用，CAS 要求当前组织绑定已启用的认证服务，密码方式要求提供存量无密码用户的补齐或重置路径。配置不满足时给出具体原因，不能保存一个导致用户无法登录的方式。Moss 的密码登录、刷新和自行改密始终不受这些切换影响。

| 入口 | 目标规则 |
|---|---|
| Moss 管理端 / Web 登录 | 固定账户密码，不读取 Sudowork 组织登录方式 |
| Sudowork 原生协议登录 | 读取 Sudowork 平台默认和组织覆盖策略 |
| Sudowork 旧兼容登录 | 同样读取 Sudowork 策略 |
| token 刷新与切组织 | 保留最初认证应用，检查账户状态、权限和该应用策略 |

建议为 Moss 增加明确的密码登录入口，例如 `/api/v1/moss/auth/login`，管理端改用它；会话/token 记录服务端签发的 `auth_app=moss|sudowork` 和认证方式。应用上下文贯穿签发、刷新、切组织、注销和修改密码，不能仅凭前端传入 `client=moss` 就跳过策略。

当前 Sudowork 的 `MossAuthClient` 也调用 `/api/v1/auth/login`、`/api/v1/auth/token`、`/api/v1/auth/send-code`、`/api/v1/auth/register`。这些既有入口必须保持 Sudowork 客户端兼容；共享刷新入口根据已验证 token 的应用上下文分发，不能把所有原生接口归到 Moss。

现有未记录应用的密码会话无法可靠区分来源。上线时让这一类旧会话重新登录，避免根据请求参数猜测归属；制定清楚的旧会话失效时间和客户端提示。API Key 等机器凭据维持其既有权限语义，不因 UI 登录方式切换被意外禁用。

发布顺序：先提供新的 Moss 认证入口，再发布使用该入口的管理端，清理旧静态资源缓存并为旧页面提供刷新提示，确认新页面可登录后才收紧旧会话规则。当前管理端的密码登录使用共享 `/api/v1/auth/token`；不能仅让旧会话退出，却让缓存页面继续从旧入口登录而被组织策略拒绝。

`/api/v1/system-config` 继续作为 Sudowork 的启动配置，改从同一策略服务投影 `login_method` 和 `auth_methods`。两者必须一致；按现有三种单选登录方式控制交互式入口，API Key 是否展示保留既有明确策略。Moss 页面固定显示密码登录，不依赖此客户端配置。

组织级登录页需要登录前的组织上下文：通过组织专属入口或用户填写企业码解析组织，再返回该组织可用的登录方式；未指定组织的公共配置只代表平台默认，不能代表所有组织。Sudowork 客户端需支持此组织选择/发现步骤，并按组织缓存登录配置；切换组织时重新获取。既有协议保持可用，旧客户端默认入口仍可返回平台默认，但不会绕过真实账号所属组织的后端校验；完成组织化展示需配套客户端更新。

认证时以账户实际所属组织和已验证的组织上下文校验，不能信任请求中任意填写的 orgId；有权限切换资源组织的管理员，也不能用目标资源组织替代身份所属组织绕过登录策略。

保留禁用账户、角色和组织数据权限检查；Moss 密码登录不自动获得管理员权限。应用标签用于区分认证策略，不是证明请求一定来自某个客户端的软件身份。

明确产品边界：本方案实现的是不同产品入口的登录策略。既然同一个用户允许用密码访问 Moss，就不能同时宣称该账号的全部访问都必须经过短信/CAS。Moss 专属入口只接受 Moss 会话，Sudowork 专属入口只接受 Sudowork 会话，不提供从 Moss 密码会话直接换取 Sudowork 会话的捷径；共用业务 API 仍按既有用户/组织授权访问，不将其描述为全账号的强制短信认证。如果要进一步要求某些业务操作必须短信/CAS，应为这些操作另设认证强度要求。

## 6. Sudowork 用户在 Moss 的密码

按用户明确要求，新建 Sudowork 手机号注册用户的 Moss 账户名为手机号，未主动设置密码时，默认密码为规范化后的手机号，存储时只保存密码哈希。原生及兼容注册路径共用初始化逻辑，同时建立 `password/moss` 身份。注册时用户已经主动设置的密码保留，不覆盖为默认值；CAS 用户没有可信手机号时不臆造默认密码。

用户可用该默认密码直接登录 Moss，之后通过所有正常用户均可访问的“个人设置 → 修改密码”自行修改。修改要求校验当前密码并遵守正式密码规则，不要求管理员权限；不因其组织采用短信/CAS 而阻止改密。不加入强制激活、额外短信验证或强制首次改密步骤。

**风险保留：手机号是公开标识，在用户主动修改前，知道手机号的人即可尝试使用相同手机号密码登录。原先建议的验证和强制改密不是本次用户选定的产品流程；采用现有登录限流和审计，也无法消除默认密码可猜测的问题。**

当前两个应用共享用户密码哈希。用户在 Moss 修改密码后，Sudowork 若采用密码登录，也使用新密码；短信验证码或 CAS 登录不受密码修改影响。无需维护两套正式密码，且不会在后续登录、注册重试或切换组织策略时把已改密码重置为手机号。

存量处理：只对能确认来源为 Sudowork、具有可信手机身份且尚无密码的用户补齐手机号密码及密码身份；保留所有已设密码、角色、状态和组织归属。缺少或冲突手机号的记录输出待处理清单，不推测或批量覆盖。既有平台管理员密码不重置，禁用用户仍不能登录。

幂等执行并提供预览、处理数和跳过原因。手机号后续变更不自动重置密码。回滚不覆盖上线后用户新设的密码；正常改密按现有会话撤销规则处理旧会话。

## 7. 实施顺序

| 阶段 | 交付与范围 |
|---|---|
| A：修正现有行为 | 短信可用性统一；Moss 专用密码入口与会话来源；明确组织覆盖、登录前组织识别与缓存；公开配置和后端策略一致；修正登录、刷新、切组织、改密回归测试 |
| B：统一平台配置 | 新页面、全局权限、普通配置/Nexus 引用、历史来源导入、两套 Router/SMS 消费者统一、版本与待生效提示 |
| C：用户密码初始化 | 手机号默认密码、普通用户自行改密入口、两个注册路径接入、存量预览与幂等补齐，保留用户已设置的密码 |
| D：上线验收 | 生产备份、导入预览、受控接管与重启、各实例版本检查、指定测试账号验证 |

默认密码和用户自行改密能力一同交付。首次上线继续保留旧环境变量和 vault 凭据作为显式回滚材料；确认接管后再单独清理。

不在本方案中重构钱包/账务模型或 Dify 组织资源模型，也不覆盖本工作区其他任务已经修改的迁移代码。

## 8. 验收标准

- 以生产同形配置测试：仅旧 `phoneAuth.tencent` 有配置、兼容模式关闭，短信就绪检查能识别实际通道；缺凭据时给出具体缺项，无法读取 vault 时与未配置区分。
- Sudowork 切短信/CAS后，Moss 账户密码登录、刷新和切组织正常；Sudowork 不允许的登录方式仍被拒绝。
- 组织 A 切换不影响组织 B；显式组织设置即使等于平台默认也不会丢失隔离；变更平台默认不覆盖已有组织选择。登录页和缓存按组织获取策略，伪造 orgId 不能绕过所属组织校验。
- 当前 Sudowork 桌面/Web 客户端的发码、注册、登录、刷新响应格式保持兼容，公开 `login_method` / `auth_methods` 与后端一致。
- 新短信注册用户可用手机号作为账号和默认密码直接登录 Moss，无强制激活/额外验证码/强制改密；可以凭当前密码自行设置新密码，组织短信/CAS 策略不阻止该操作。
- 已设置密码的存量用户不被覆盖；登录、注册重试、手机号变更和组织切换均不重置密码；禁用用户仍被拒绝。Moss 改密后 Sudowork 密码登录使用新密码，短信/CAS 登录保持正常。
- Moss 与 Sudowork 专属 API 拒绝另一应用会话。
- 平台配置不随组织切换；普通组织管理员直接调用新旧平台配置/凭证接口均被拒绝；Dify/QMS/Router 业务资源仍受原有归属限制。
- 导入与接管前后 URL、管理员身份、模板和密钥来源一致；接管后旧 env 不覆盖页面值；清空不恢复旧密钥。
- 保存失败不破坏生效版本；重启前后状态正确；多实例可识别未生效节点；旧支付订单在轮换后仍可处理。
- 公开接口和普通组织接口不泄露平台管理密钥。测试短信、实际支付测试单独执行，不由配置检查触发。

## 10. 兼容开关当前控制的范围（2026-09-24 补充）

`sudoworkCompatibility.enabled` 控制按 Host 暴露的整套兼容应用，而不是当前 Sudowork 注册功能的总开关。仅在开关开启、Host 精确命中 `hosts`、请求方法和路径命中已注册兼容路由时，优先进入兼容处理器；否则交给 Moss 原生处理器，原生无对应接口才返回 404。

兼容应用注册的接口分组包括：认证（短信/密码注册登录、refresh、logout、旧管理员登录、CAS 回调与交换）、用户资料、系统/租户配置、企业/用户/邀请码管理、助手/技能目录、Dify 对话增强与知识库、充值/积分/额度/账单、QMS 遥测/崩溃/监控。Dify/QMS 等是否注册或可执行还取决于各自运行时与凭据配置，打开兼容开关不等于自动启用这些服务。

路径重复不等于逻辑相同：`/api/v1/auth/login`、`/api/v1/auth/register`、`/api/v1/auth/send-code` 在原生与兼容应用都有实现。当前生产使用原生版本；为现有域名打开兼容分流会改变相同 URL 对应的认证协议。

`/api/moss/v1/operations/...` 根据独立白名单优先分流，不依赖兼容开关，启动时始终创建相应应用。例：`GET/PUT /api/moss/v1/operations/system-config` 在内部映射到 `/api/v1/admin/system-config`；邀请码、充值管理、知识库及 QMS 管理也有此类独立入口。该入口仅映射白名单中的方法/路径，不是开放全部兼容路由。

开关还控制旧 JWT/Redis 会话初始化、兼容登录限流和兼容 CAS 服务创建；`smsRuntimeAvailable` 被错误地绑定到这个开关，影响独立后台入口的短信校验。后续方案需要把公共短信能力及组织认证服务的就绪性从旧协议暴露开关中分离。

依据：`src/server/api/compat/sudowork/hostDispatch.ts`、`sharedOperationalRoutes.ts`、`app.ts` 及各注册路由模块，`src/server/startStandaloneServer.ts`。
