用户明确要求：完整实现原始方案 10.3 及 P0、P1 涉及的盒子运维能力；全部部署在 Docker 中，Docker Compose 为唯一部署入口；每项功能必须实际可用；高内聚、低耦合、最小修改，聚焦需求；结论只能依据已执行的验证，不将模拟调用、HTTP 200 或程序正常退出等同于业务成功。计划文档仅在用户明确授权后编写。

验收环境：本机 Docker Desktop Linux 引擎 29.1.3，Compose 项目 `park-box`。本记录仅说明本环境已执行的验证，不表示其他硬件、模型提供方或生产数据规模已验收。

## 初始化和故障验证

真实初始化完成组织绑定、三种园区角色、政策导入、知识库构建、Assistant 发布、四个快捷问题和三个渠道入口。最终交付任务 `4fc1929e-0ac0-4d6e-9e2a-b6edcbfd3b41` 成功，验证公开流式回答、数据库咨询记录及可打开的政策引用。

全部中断测试结束后，最终版本 3 交付复验任务 `a9c32c88-f542-421d-a2b8-9ca476fb3428` 成功；四个容器运行，`/readyz` 返回 `ok:true, ready:true`，实际镜像与组件版本、模型推理、政策检索、公开咨询记录和引用预览均通过。故意构造的三个负向升级包及签名已移入运维卷 `acceptance/upgrade-fixtures/`，不再出现在管理员升级列表中。

操作重复提交返回相同任务，执行中的第二项操作被拒绝。备份测试任务 `abc74cab-3a37-4e5e-9987-e799f0a97284` 在业务容器停止后中断运维进程；启动运维容器后恢复业务并完成真实问答验证，任务保持 `failed/interrupted`，`recovered:true`。显式 Docker `kill` 不自动重启容器；本次恢复验证包括重新启动运维容器。

脚本补上显式启动后，第二次中断任务 `4386773b-3947-4452-a206-8ac492f32844` 也通过相同验证，没有依靠人工补充启动步骤。

早期备份任务因 SQLite 验证生成 WAL 边文件失败，修复为对停写副本进行 immutable 校验，后续真实备份与恢复通过。失败备份不列为可选恢复文件。首次回滚任务 `69d4db0a-0709-4576-9066-6c3818c423c2` 遇到模型 `fetch failed`，原状态保护恢复成功；重试回滚通过。

重复完整依赖构建耗尽 C 盘空间，造成 Docker 停止，不能将该次自动恢复记为成功。恢复空间并启动 Docker 后，发现 Docker 残留无名称失效记录使 inspect 返回 404；修复识别并补回归。恢复重试任务 `bc1820a8-5474-4c34-a66b-5b435ce73e4e` 成功，随后完整自动回滚重测通过。最终页面利用已验证的版本 2 服务镜像和本地已安装依赖构建版本 3，没有重复安装全部依赖。原有业务数据卷保留。

## 检查范围

7 项 Python 专项测试通过，包括真实 Ed25519、归档路径、SQLite、任务信息过滤及残留容器识别。6 项 runner readiness 测试与 2 项原盒子测试通过；原盒子测试中的执行器是模拟的。Park 类型检查、修改文件 lint、Python 编译和 Git diff 空白检查通过。Moss 类型错误基线检查为服务端 104 个错误、基线 104，不表示整个仓库类型检查无错误。

备份和升级暂时停止业务容器，恢复完成后才解除维护。备份含凭证数据，存放在独立运维卷并限制权限；签名私钥不挂载到常驻运维容器。验收错误和持久任务继续保留，便于复查。
